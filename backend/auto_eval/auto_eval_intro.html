ResearchAgent / backend / auto_eval

auto_eval 是一层“真实运行 + 自动评分 + 报告归档”的评测编排框架

它不是一个通用第三方库，而是项目内部自建的 benchmark/evaluator 系统。核心思路是： 通过 HTTP 真正驱动 backend 的 workspace、session、chat、files、assets、trace， 然后对每个 turn 做规则检查、trace 检查、artifact 检查和 judge 评分，最后把结果保存到本地 run 目录，并可回写到 workspace 的 memory/packs。

一句话定位

如果把主系统看成“科研智能体运行时”，那 auto_eval 就是它外面的测试跑台： 负责喂场景、跑对话、抓痕迹、验产物、算分数、产报告。

它解决的核心问题

过去只能人工翻最终回答，看不到 agent 在长流程里到底有没有读对材料、有没有生成对的文件、有没有在不该外推的地方乱讲。 auto_eval 就是把这些能力结构化、可重复、可批量地跑起来。

真实链路评测

  • 真实创建 workspace
  • 真实上传附件
  • 真实调用 /api/chat
  • 真实读取 history / files / trace

不只看回答文本

  • 检查关键术语和危险表述
  • 检查工具调用与 trace 行为
  • 检查目标 artifact 是否真的落盘
  • 检查 hallucination 子指标

适合长时 benchmark

  • 终端实时打印进度和流式事件
  • 按 turn 落 checkpoint
  • 支持 resume
  • 最终产出 markdown / json / html 报告

整体架构

主流程可以概括为 CLI → Scenario Loader → Runner → Backend HTTP → Evaluate → Report。

01 CLI

接收 --scenario、--source-root、--resume 等参数，组装运行配置。

02 Scenario Loader

加载某个场景目录里的问题集 JSON 和 runbook Python 模块。

03 Runner

创建 workspace/session，按 session 和 turn 顺序编排整场评测。

04 HTTP Backend

通过现有 API 调 workspace、chat、files、assets、history、trace。

05 Turn Evaluation

对回答内容、trace、artifact、judge 结果和临时目录进行检查。

06 Report & Store

把 turn 结果、summary、console replay、scoreboard 写入本地并镜像到 workspace。

目录里的关键文件

  • cli.py入口。解析命令行参数，构造 EvalConfig，启动 EvalRunner。
  • runner.py核心编排器。负责 turn 执行、SSE 消费、trace 拉取、打分、checkpoint、summary 生成。
  • http_backend.py后端 API 客户端封装，统一处理 workspaces / sessions / chat / files / assets。
  • scenario_loader.py按目录动态发现并加载 scenario package。
  • run_store.py本地结果存储层，保存 events.jsonl、turn 结果、checkpoint、终端回放。
  • judge.py当前的 judge 占位实现，暂时是启发式评分，不是独立大模型裁判服务。
  • markdown_reporter.py生成场景 summary 和总体 scoreboard 的 Markdown。

Scenario 目录怎么理解

  • B_questions_and_eval_methods：文献与 Concept 闭环
  • C_questions_and_eval_methods：另一类闭环场景
  • D_questions_and_eval_methods：另一类闭环场景
  • E_questions_and_eval_methods：另一类闭环场景

每个场景目录通常包含： 问题集 JSON、runbook、content checks、trace checks、artifact checks、hallucination checks、llm judge prompt 生成逻辑。

Scenario Package 的工作方式

这套系统的可扩展性主要就靠 scenario package。你给它一个目录，它就能把“要问什么、要传什么、期待什么、怎么评分”整包加载进来。

问题定义

在 *_scenario_questions.json 里定义 scenario 元信息、sessions、dialogue turns、用户上传文件、预期 artifact、关键术语、禁词和场景 focus。

评分注册

在 registry 里把每个 turn 展开成多条 criterion，通常至少包含 content、trace 或 artifact、以及 llm judge 三类评分点。

运行蓝图

在 runbook 里定义 evaluate_turn 和 summarize_scenario，决定一个 turn 最终如何汇总成可落盘结果。

评测指标怎么写

指标不是单独一张 Excel 表，而是三层拼起来的：场景 JSON 先声明 turn 要考什么，registry 把它拆成 criterion，场景 Python 模块再实现具体扣分，最后 runner 把分数汇总成 turn 级结果。

声明层

在 *_scenario_questions.json 里写 key_terms、 forbidden_terms、 expected_artifacts、 binary_grounding_required、 requires_workspace_memory_from_prior_sessions。

规则层

在场景自己的 content_checks.py、 trace_checks.py、 artifact_checks.py、 hallucination_checks.py 里写扣分逻辑。

汇总层

在 runbook.py 里拼出 content_result、 trace_result、 artifact_result、 llm_job，再由 runner 合成 final_turn_score。

01 Scenario JSON

声明关键术语、禁词、预期文件、binary grounding、memory 依赖等。

02 Registry

把 turn 展开成 content、trace/artifact、judge 三类 criterion。

03 Runner

真实执行 turn，抓 SSE、history、trace、artifact probe。

04 Checks

调用 content/trace/artifact/hallucination 规则模块。

05 Judge

当前用启发式 judge 给出第三路评分。

06 Final Score

合并各路分数，写入 turn 结果和 scenario summary。

一次 turn 内部发生了什么

  1. 根据 user_upload 找到文件并上传，支持同 workspace 内缓存复用。
  2. 调用 /api/chat，用 SSE 消费 token、tool_start、tool_end、done、error。
  3. 取回 session history，得到最终 assistant 文本。
  4. 读取 context_trace/<session_id>.json 的增量 trace。
  5. 把 expected artifact 和 temporary_dir 快照抓到本地 probe 目录。
  6. 调用 scenario 的 evaluate_turn 产出 content/trace/artifact/llm_job。
  7. 再叠加 heuristic judge，算出 final score。
  8. 把 turn 结果落到本地，并写 checkpoint。

为什么它比“只看回答”更强

  • 能判断模型有没有真的读文件，而不是只凭文件名胡猜。
  • 能判断文件有没有真正写到 memory/。
  • 能判断跨 session 时有没有复用 workspace memory。
  • 能为 binary grounding、source honesty、unsafe transfer 这类问题留证据。

产出结果长什么样

本地 run 目录

  • run_manifest.json
  • events.jsonl
  • scenarios/<scenario>/*.json
  • scenarios/<scenario>/summary.md
  • reports/overall_summary.json
  • reports/report.md
  • reports/terminal_replay.html
  • checkpoints/completed_turns.json

真实 workspace 回写

  • memory/packs/EVAL_RUN_..._INDEX.md
  • memory/packs/EVAL_RUN_..._SCOREBOARD.md
  • memory/packs/EVAL_RUN_..._B_SUMMARY.md 等场景摘要

这意味着评测不是只存在本地脚本里，之后也能在前端像普通 workspace 一样回看。

快速运行示意

先启动 backend，再在 backend 目录里运行 python -m auto_eval.cli。

python -m auto_eval.cli \ --backend-url http://127.0.0.1:8002 \ --scenario B \ --source-root <你的真实资料根目录>
--session-limit 只跑前几个 session
--turn-limit 只跑前几个 turn
--resume 从 checkpoint 恢复
--judge-mode off 先测链路
结论： auto_eval 的本质不是“问答页面”或“规则文件集合”，而是一套围绕科研智能体后端搭建的自动 benchmark 编排层。 它把真实运行、过程证据、结果评分和事后复盘连成了一套闭环。 评测指标的详细写法可继续看 auto_eval_metrics_intro.html，汇报版可看 auto_eval_metrics_brief.html。
