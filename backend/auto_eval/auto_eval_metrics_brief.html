Briefing Page

auto_eval 的评测指标，本质上是在考“回答对不对、过程真不真、文件落没落、有没有乱讲”

这套 benchmark 不只看最终回答，而是把 turn 级评测拆成内容、trace/产物、judge、幻觉风险四个维度，再由 runner 汇总成最终得分和场景报告。

总介绍页 指标详细版

汇报时最该讲的 4 件事

1 指标先在场景 JSON 里声明，例如 key_terms、forbidden_terms、expected_artifacts、binary_grounding_required。
2 每个 turn 默认拆成三类 criterion：content、trace/artifact、judge。
3 打分不只看文本，还看有没有读文件、有没有写 memory、有没有真实二进制解析痕迹。
4 幻觉指标单独做 flag 和 rate 统计，形成风险画像，不只是一个平均分。

指标层次

声明层

题目 JSON 写清楚这一轮要考什么、有什么禁区、需不需要 artifact、需不需要 binary grounding。

规则层

场景自己的 content_checks.py、trace_checks.py、artifact_checks.py 负责实现扣分。

汇总层

runbook.py 和 runner.py 负责把各路子分数组装成 final_turn_score 和 scenario summary。

简化流线图

Scenario JSON

声明 turn 的考点与约束。

Registry

拆成 content / trace-or-artifact / judge。

Runner 执行

真实跑 chat，抓 SSE、history、trace、artifact。

Checks + Judge

计算内容分、过程分、产物分、judge 分和幻觉 flags。

Summary

输出 turn 分数、hallucination rates、scenario 报告。

当前 final score 公式

默认合成

final_turn_score = average(content, artifact/trace, judge)

可选附加项

若某轮配置了 temporary_expectations，还会把 temporary dir 检查分加进平均值。

当前实现要点

强项

真正覆盖“回答内容 + 工具行为 + 文件真实性 + 风险率”四条线，不是只看聊天文本。

现状限制

LLM judge prompt 已经设计好，但当前实际执行还是 HeuristicJudge，尚未接独立大模型裁判。

一句话结论： auto_eval 的指标体系是一套分层式 benchmark 机制。它把“题目设计、过程证据、结果真伪、幻觉风险”连起来，形成 turn 级自动评测闭环。
