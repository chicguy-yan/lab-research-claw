auto_eval / Metrics Guide

这套自动评测集的指标，不是单独一张表，而是“JSON 声明 + Python 规则 + Runner 汇总”三层拼起来的

也就是说，一个 turn 想测什么，先在场景 JSON 里声明；怎么扣分，写在场景自己的 content / trace / artifact / hallucination 模块里；最后由 runbook 和 runner 统一汇总成 final_turn_score、hallucination rates 和 scenario summary。

一句话理解

如果说 benchmark 问题集在描述“我要考模型什么能力”，那指标实现层就是“我准备怎样根据回答文本、trace、生成文件和风险信号来扣分”。

一、指标先在场景 JSON 里声明

每个 turn 的“评测需求”先写在 *_scenario_questions.json 里。 这里不直接算分，而是声明这个问题该关注什么、需要什么证据、需要输出什么文件。

核心字段

  • key_terms回答中应该覆盖的关键词或概念锚点。
  • forbidden_terms不应出现的危险表述或错误迁移。
  • content_focus内容评分重点，告诉规则层这轮的主目标是什么。
  • trace_focus过程侧要求，例如要不要读 PDF、要不要真正写文件。
  • llm_focusjudge 应重点盯的高层判断维度。
  • expected_artifacts本轮必须产出的文件路径、必须包含的 section。
  • binary_grounding_required要求不能只靠 quick summary，必须有真实二进制解析痕迹。
  • requires_workspace_memory_from_prior_sessions要求本轮显示复用前面 session 的 memory 结果。
  • eval_tags给这轮指标打标签，便于 registry 和解释层整理。

这个层的作用

  • 把 benchmark 设计者的评测意图结构化下来。
  • 把“我要考什么”从 Python 算分逻辑里抽离出来。
  • 让不同场景可以各自写自己的 turn 要求，不共用死板模板。
  • 给后续 content / trace / artifact / judge 模块提供统一输入。
{
  "key_terms": ["OAT", "PCET", "ClO2", "Co(IV)=O"],
  "forbidden_terms": ["PMS直接活化", "芬顿主线"],
  "binary_grounding_required": true,
  "expected_artifacts": [],
  "requires_workspace_memory_from_prior_sessions": false
}

二、registry 把一个 turn 拆成多条 criterion

场景 registry 负责把 JSON 里的一个 turn，展开成可执行的评分条目。B 场景里，每个 turn 默认至少有三条： C1 content-rule、C2 trace/artifact、C3 llm-judge。

C1 内容指标

回答有没有覆盖关键术语、有没有踩禁词、有没有体现 prior memory、有没有显式提到目标 artifact 名称。

C2 过程或产物指标

如果该 turn 要生成文件，就检查 artifact；否则就检查 trace、读文件行为、binary grounding 和 memory 读取痕迹。

C3 Judge 指标

先根据 turn 类型构造不同 judge prompt。当前代码里 prompt 已有，但最终实际评分仍由启发式 judge 计算。

三、指标真正怎么写

真正的扣分逻辑，写在场景自己的 Python 模块里。B 场景是最典型的例子。

content_checks

  • 命中至少若干个 key_terms
  • 命中 forbidden_terms 就扣分
  • 该复用 prior memory 却没体现也扣分
  • 要生成 artifact 却连文件名都没提，会轻扣

trace_checks

  • 需要写 artifact 却没看到 write_file
  • 上传了文件却没看到读文件动作
  • binary turn 却没有 terminal/python_repl
  • 依赖 prior memory 却没看到 memory 读取痕迹

artifact_checks

  • 预期文件不存在，重扣
  • 缺少 required sections，继续扣
  • 写到 memory/ 下的文件若无 source_assets frontmatter，也会扣

四、幻觉指标不是单轮主分，而是额外 flags + 汇总率

这类指标的写法和 content/trace 不一样。它更多是先给每个 turn 打风险标记，再在 scenario 级聚合成 rate。

单轮 flags 示例

  • unsupported_specificity：无依据捏造很多具体数值/页码/定量细节
  • absolute_overclaim_hits：用了“已经证明”“完全证实”这类强断言
  • source_confusion_hits：把 note/ppt/docx 压缩结论说成 paper 原文直接结论
  • trace_free_binary_certainty：没做二进制解析，却说“第几页明确证明”
  • cross_system_overtransfer：把 PMS/Fenton/Ce 旁支结果直接迁移成 chlorite 已证实事实

聚合方式

每个 turn 只记录 flag 是否触发。到了 scenario summary 阶段，再把这些 flag 统计成 raw_counters 和 rates。 所以 hallucination 指标更像“风险画像”，而不是单一最终得分。

五、评测流线图

下面这张图展示的是，一个 turn 从“题目声明”到“最终得分和报告”的完整路径。

STEP 01 Scenario JSON

声明 key_terms、forbidden_terms、expected_artifacts、binary_grounding_required 等 turn 要求。

STEP 02 Registry

把一个 turn 展开成 C1 content、C2 trace/artifact、C3 judge 三类 criterion。

STEP 03 Runner 执行 turn

上传附件，调用 /api/chat，消费 SSE，读取 history、trace、artifact probe 和 temporary_dir 快照。

STEP 04 Runbook

调用场景自己的 evaluate_turn，得到 content_result、trace_result、artifact_result、llm_job、hallucination_flags。

STEP 05 Judge / Temp Checks

Runner 再调用 judge，并在有配置时叠加 temporary_expectations 检查。

STEP 06 Final Score

主分按 content + artifact/trace + judge (+ temp) 取平均，生成 final_turn_score。

STEP 07 Summary & Reports

把 turn 结果写入 JSON，按 scenario 汇总平均分和 hallucination rates，再生成 markdown / html 报告。

六、当前 final score 是怎么合成的

当前 runner 的总分合成逻辑比较直接，不是复杂加权模型。

默认主分

final_turn_score =
  average(
    content_result.score,
    artifact_result.score 或 trace_result.score,
    judge_result.score
  )

可选附加项

如果某个 turn 配了 temporary_expectations， runner 会再把 temporary dir 检查分也纳入平均值。 所以最终得分来自“文本结果 + 过程证据 + 产物真实性 + 补充检查”。

七、为什么说“LLM judge 目前还是半成品”

已经有的部分

每个场景已经实现了 judge prompt builder，会根据 turn 是否涉及 artifact、binary grounding 等情况切换不同 prompt 角色和 focus。

当前实际评分方式

Runner 现在调用的是 HeuristicJudge。也就是用关键词命中、禁词、工具痕迹、是否提到 memory/ 等启发式规则给 judge 分，而不是再发一个真正的大模型裁判请求。

八、如果你要改指标，通常改哪几层

改“考什么”

编辑场景 JSON。增删 key_terms、forbidden_terms、expected_artifacts、focus 描述。

改“怎么扣分”

编辑该场景的 content_checks.py、trace_checks.py、artifact_checks.py、hallucination_checks.py。

改“怎么汇总”

编辑场景 runbook.py 或总控 runner.py，调整 final score 的组合逻辑。

九、源码文件路径索引

如果你要顺着代码继续看，下面这些文件就是“指标怎么声明、怎么打分、怎么汇总”的主入口。

  • backend/auto_eval/B_questions_and_eval_methods/B_scenario_questions.jsonB 场景每个 turn 的评测字段声明。
  • backend/auto_eval/B_questions_and_eval_methods/scenario_B_registry.py把 turn 展开成 content / trace-or-artifact / judge 三类 criterion。
  • backend/auto_eval/B_questions_and_eval_methods/scenario_B_content_checks.py关键术语、禁词、prior memory 信号等内容侧扣分规则。
  • backend/auto_eval/B_questions_and_eval_methods/scenario_B_trace_checks.py读文件、write_file、binary grounding、memory 读取痕迹等 trace 侧规则。
  • backend/auto_eval/B_questions_and_eval_methods/scenario_B_artifact_checks.py预期文件是否存在、section 是否齐全、frontmatter 是否完整。
  • backend/auto_eval/B_questions_and_eval_methods/scenario_B_hallucination_checks.py幻觉 flags 和 scenario 级风险率汇总。
  • backend/auto_eval/B_questions_and_eval_methods/scenario_B_llm_judges.py按 turn 类型切换 judge prompt 和结构化输出 schema。
  • backend/auto_eval/B_questions_and_eval_methods/scenario_B_runbook.py把各类子分数组装成 turn evaluation 结果。
  • backend/auto_eval/runner.py真实执行 turn，并把 content / artifact-or-trace / judge / temp checks 合成 final_turn_score。
  • backend/auto_eval/judge.py当前启发式 judge 的实际实现。
总介绍页 汇报版
结论： auto_eval 的评测指标写法本质上是一套分层设计。 JSON 负责声明评测意图，场景 Python 模块负责实现扣分细则，runner 负责把这些局部结果组装成 turn 分数、hallucination 汇总和最终报告。
