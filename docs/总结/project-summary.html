Step 1：项目骨架

一句话定义

面向实验学科的本地化科研 AI Agent 系统，通过"文件即记忆 + 技能即插件 + 全链路可追溯"三大机制，将 180 天实验周期中的文献、实验、机理验证、阶段汇报等高频场景编排为可闭环、可回放、可沉淀的工作流。

它解决的真实问题

科研人员（尤其是硕博生）在长周期实验中面临三重压力（来自 项目最终实现效果.md 用户访谈）：

痛点 1记忆断裂

实验跨度 180 天，阶段汇报 10+ 次，每次都要从头翻记录、找数据、拼 PPT。导师追问"上次那个对照做了没"时答不上来。

痛点 2证据链断裂

结论和数据之间缺乏可追溯的锚点。"Ce 加多了峰不稳定"背后到底对应哪个 csv、哪张照片、哪次实验条件？说不清就会被 challenge。

痛点 3认知负担过重

被导师 challenge 后容易陷入自我怀疑，分不清"是我不行"还是"变量没控好"。缺乏结构化排查框架把不确定性收敛为可验证的步骤。

与普通 AI 助手的核心区别

维度普通 AI 助手OpenClaw
记忆单次对话窗口，关掉就忘三层文件记忆（Identity/Timeline/AtomNotes），180 天持久化
证据回答基于训练数据，无法引用用户实验文件每条结论挂 trace 回指（文件路径 + 用户原话 + 证据类型）
透明度Prompt 拼接是黑盒全链路可回放：读了什么文件、为什么读、有没有被裁剪
技能固定能力，不可扩展Skills 即 Markdown 说明书，拖入文件夹即用
交付物纯文本回复结构化三卡落盘（Evidence/Task/Result），事实区与推断区分离

最核心的产品抽象："三卡落盘"

来源：项目最终实现效果.md golden test 剧本

Evidence 卡memory/evidence/EVD-*.md

证据锚点——用户原话 + 文件路径 + 数据摘要，只记录事实

Task 卡memory/tasks/TSK-*.md

任务结构——Claim + Protocol + Run + 事实区/推断区，把模糊需求拆成可执行步骤

Result 卡memory/results/RES-*.md

交付物——PPT 大纲/SOP/证据链，每条结论挂 trace 回指和 assumptions 声明

本质：把不确定的 LLM 行为包进确定的"证据采集 → 结构化输出 → 可追溯落盘"外壳里。

100 字摘要

面向实验学科的本地化科研 AI Agent。三层文件记忆（Identity/Timeline/AtomNotes）管理 180 天实验周期；ContextOrchestrator 智能选择上下文，PromptBuilder 7-Block 结构化拼接，TraceWriter 全链路审计；输出为 Evidence→Task→Result 三卡闭环，事实与推断强制分离，每条结论挂证据回指。Skills 系统支持 Markdown 说明书即插即用。

3 个最关键关键词

File-first Memory
文件即记忆
三层 Markdown 文件系统替代向量数据库，人类可读可改可追溯
Evidence-traced Delivery
证据链交付
每条输出挂 trace 回指，事实与推断强制分离
Skills-as-Instructions
技能即说明书
Skill 是教 Agent 如何用工具的 Markdown，非预置函数，拖入即用

3 个最大亮点

亮点 1：三层记忆架构解决长周期"记忆断裂"

按"可变性"分层，而非简单 RAG 检索：

  • Layer1（Identity）：项目北极星、判据、实验室约束 —— 几乎不变，每轮必读
  • Layer2（Timeline）：180 天总览 → 阶段 → 周 → 日 —— 中频更新，按意图选择性注入
  • Layer3（AtomNotes）：Concept/Task/Pack 原子资产 —— 高频创建，按相关性 Top-K 注入

ContextOrchestrator 按"稳定→变化→本轮相关"优先级自动选择注入文件，并在 trace 的 context_read[] 中记录选择原因和裁剪状态。

亮点 2：全链路透明可回放

  • context_read[]：本轮读了哪些文件、为什么读、是否被裁剪（path/layer/why/status）
  • tool_calls[]：调用了什么工具、输入输出是什么
  • prompt 元数据：System Prompt 的 7-Block 完整结构

Demo 剧本中 Result 卡每条结论后挂 (trace:EVD-20260204-001) 锚点，可追溯到原始数据文件。

亮点 3：从"回答问题"到"工作台交付"

  • 输入不是"问题"，而是"证据材料"（实验本照片、XRD csv、文献 pdf）
  • 输出不是"回答"，而是"结构化交付物"（PPT 大纲 + 每页中心句、实验 SOP + 验收标准）
  • 过程不是"一次性生成"，而是"A/B 轻量试探 → 证据采集 → 三卡落盘 → 沉淀为技能"

3 个最大风险

风险 1冷启动成本高

三层记忆的威力建立在 Identity 层被正确填充的前提上。BOOTSTRAP.md 协议采用轻量试探策略，但实际完成率未经真实用户验证。

风险 2前端未完成

Phase 1-5.3 后端已完成（92 个 Python 文件、8 个单元测试），但 Phase 6 前端三栏 UI 尚未开发。有基础 frontend/index.html 原型。

风险 3LLM 指令遵循不稳定

三卡落盘质量依赖 LLM 能力。通过 SOUL.md 硬约束 + test_system_prompt_contract.py 验证结构，但语义层面仍需人工审查。两条 golden test 覆盖面有限。

Step 2：架构地图

总体分层

┌─────────────────────────────────────────────────────────────┐
│                      Control Plane                          │
│  SOUL.md / IDENTITY.md / AGENTS.md / USER.md / TOOLS.md    │
│  → 定义 Agent "如何工作"的硬协议，优先级最高                   │
├─────────────────────────────────────────────────────────────┤
│                       Data Plane                            │
│  Layer1: identity/   Layer2: timeline/   Layer3: atoms/     │
│  → 存放长期事实、时间推进、原子资产，服从 Control Plane         │
├─────────────────────────────────────────────────────────────┤
│                      Trace Plane                            │
│  context_trace/{session_id}.json                            │
│  → 全链路审计：读了什么、写了什么、缺什么、为什么               │
└─────────────────────────────────────────────────────────────┘

Control Plane：定义"Agent 如何工作"

文件职责关键内容
SOUL.md行为准则科研三问（What/So what/Now what）、证据标准（硬约束：所有结论必须带证据类型+数据路径+对照+判据）、执行真实性（不脑补执行结果）
IDENTITY.md身份定义Name/Role/Domain/Vibe，"像靠谱师兄+严谨审稿人"
AGENTS.mdAgent 管理协议技能协议、记忆协议、工具边界
USER.md用户信息用户偏好与输出约束
TOOLS.md工具调用约定5 个核心工具的使用规范
BOOTSTRAP.md首次初始化协议识别语义边界、引导初始 assets、生成最小 memory 骨架

产品判断：Control Plane 的本质是把 LLM 的不确定性关进确定性的笼子里。科研场景对"幻觉"零容忍——SOUL.md 在 Prompt 最高优先级位置注入硬约束，不靠 LLM 自觉。

Data Plane：存放"Agent 知道什么"

Layer1：Identity（长期稳定）

memory/identity/
├── user.md           # 用户偏好与输出约束
├── project.md        # 项目北极星、主线假设、指标、术语表、判据（最关键）
├── lab_context.md    # 实验室现实约束：仪器/表征/命名/污染风险
└── context_budget.md # 单回合上下文预算与截断策略

产品判断：project.md 是整个记忆系统的锚点。ContextOrchestrator 每次对话都优先注入它，因为"判据"决定了 AI 建议是否靠谱。没有判据的建议就是幻觉。

Layer2：Timeline（中频更新）

memory/timeline/
├── 180d_index.md              # 180天总览：阶段划分、里程碑、风险雷达
├── phases/                    # 阶段文档（P01-P05）
├── weeks/                     # 周报
├── days/                      # 日志
└── stage_reports/             # 阶段汇报（R01-R10）

产品判断：导师问"这两周做了什么"时，ContextOrchestrator 根据意图自动拉取 time_range 内的 weeks/days + 上一期 stage_report，不需要用户手动指定。

Layer3：AtomNotes（高频创建）

memory/concepts/    # Concept：研究主题容器（你在验证什么）
memory/tasks/       # Task：验证任务（= Claim + Protocol + Run）
memory/packs/       # Pack：交付包（PPT/机理证据链/论文写作/图集）

产品判断：Concept 驱动 Task，Task 结果汇聚成 Pack。这不是发明的抽象，而是科研工作流的自然结构——以前散落在 Excel/Word/PPT 里，现在被统一建模。

Trace Plane：记录"Agent 做了什么"

// context_trace/{session_id}.json — Envelope Schema
{
  "messages": [...],     // SessionManager 读写：OpenAI messages 数组
  "traces": [...],       // TraceWriter 读写：审计信息数组
  "prompt": {...}        // PromptBuilder 写入：本轮 System Prompt 元数据
}

// trace 的 context_read[] 最小字段
{
  "path": "memory/identity/project.md",
  "layer": "memory_identity",
  "why": "项目北极星与判据，每轮必读",
  "status": "full"   // full | truncated | skipped
}

产品判断：Trace 的价值是建立用户信任。ChatGPT 给你答案，你不知道它基于什么。OpenClaw 告诉你"我读了你的 project.md 判据 + 上周实验日志 + XRD csv，基于这些得出结论"。

核心模块职责

编排ContextOrchestrator — graph/context_orchestrator.py

扫描 workspace memory 目录，基于用户消息做意图识别（关键词匹配），按"稳定→变化→本轮相关"排序推荐文件，生成 Memory Map。失败时安全降级为全量默认注入。

产品判断：这是"AI-native 产品"与"套壳 ChatGPT"的分水岭——智能上下文选择，读什么、不读什么、为什么，都有据可查。

拼接PromptBuilder — graph/prompt_builder.py

将 Control Plane + Memory Map + Skills Snapshot + 工具说明 + 可信元数据拼接为 7-Block System Prompt：Identity → Tooling → Workspace → Metadata → Control Plane → Skills Snapshot → Memory Map。

产品判断：Prompt Engineering 不是写一段好的提示词，而是设计一套可维护、可迭代、可审计的 Prompt 拼接系统。每个 Block 可独立修改和测试。

追踪TraceWriter — graph/trace_writer.py

每轮对话完成后，将工具调用列表 + Prompt 元数据写入 trace 文件。读取现有 envelope（保留 messages），追加 trace 条目，写回文件。

技能SkillLoader — graph/skill_loader.py

读取 system/workspace skills registry，生成 SKILLS_SNAPSHOT.md 菜单摘要注入 Prompt。Agent 据此自主决策是否 read_file 读取完整说明书。渐进式披露，避免 Prompt 膨胀。

产品判断：Skill 不是代码插件，是 Markdown 说明书。用户可以自己写，行为可审计，扩展不需要改代码。

执行AgentManager — graph/agent.py

使用 LangChain create_agent（LangGraph runtime）构建 Agent，流式执行并 yield SSE 事件：token / tool_start / tool_end / new_response / error。

隔离WorkspaceRuntimeRegistry — runtime/workspace_registry.py

Phase 5.3 核心。SharedAgentResources 共享 LLM + FetchURLTool（进程级单例），WorkspaceRuntime 隔离 SessionManager + workspace-scoped tools（CWD 绑定到 workspace 目录）。

产品判断：用户心智模型是"我有多个课题，每个课题有自己的记忆和文件"。Workspace 隔离解决的是产品问题，不是技术问题。

单次对话完整流线

用户发送消息
    │
    ▼
[1] WorkspaceRuntimeRegistry.get_runtime(workspace_id)
    → 获取对应 workspace 的 SessionManager + Tools
    │
    ▼
[2] SessionManager.load_session(session_id)
    → 获取历史消息（合并连续 assistant 消息）
    │
    ▼
[3] ContextOrchestrator.generate_memory_map(message, workspace_dir)
    → 扫描 memory 目录 → 意图识别 → 推荐文件 → 输出 Memory Map
    │
    ▼
[4] SkillLoader.get_snapshot()
    → 生成 SKILLS_SNAPSHOT.md 菜单
    │
    ▼
[5] PromptBuilder.build(workspace_dir, memory_map, skill_snapshot, tools)
    → 拼接 7 Block System Prompt
    │
    ▼
[6] AgentManager.astream(messages, system_prompt, tools)
    → LangChain create_agent → 流式执行
    → SSE: token / tool_start / tool_end / new_response
    │
    ▼
[7] SessionManager.save_message → 持久化 messages
    │
    ▼
[8] TraceWriter.write_trace → 持久化 traces
    │
    ▼
[9] SSE: done {session_id, trace_path}
    → done 在 trace 写入完成后才发送（解决竞态条件）

Step 3：能力地图

从 AI 产品经理 / AI Agent 面试视角，抽取本项目体现的六项核心能力。

能力 1：场景拆解

证据
  • 从用户访谈中提炼 2 类托管模式——DDL 型（"今晚组会要交付"）和认知流动型（"被 challenge 到不自信，先搞清楚为什么"），不是拍脑袋分的，而是从用户原话中抽象出来的。
  • PRD §4.6 定义了 7 个高频场景（合成 checklist、实验矩阵、机理证据链审计、表征审计、阶段汇报、写作结构、CSV 作图），每个场景有明确的"读什么→写什么"策略。
  • 把科研周期拆成"阶段→周→日"三级粒度，对应 Layer2 的 phases/weeks/days 目录结构——从"导师问你这两周做了什么"这个真实场景倒推。

简历表达：基于用户访谈提炼 2 类托管模式（DDL 交付型 / 认知探索型）和 7 个高频科研场景，将 180 天实验周期拆解为"阶段→周→日"三级粒度，每个场景定义明确的上下文读写策略，驱动 ContextOrchestrator 的意图识别与文件选择逻辑。

面试追问
  • "你怎么确定这 7 个场景是高频的？" → 来自用户访谈 + 科研工作流分析。意图识别失败时降级为全量默认注入，确保不漏。
  • "DDL 型和认知流动型的区别在产品层面意味着什么？" → 不同的上下文选择策略和输出结构。系统通过 A/B 轻量试探让用户自己选，而不是 AI 猜。
  • "如果用户需求不属于这 7 个场景？" → 降级为通用模式。MVP 不追求 100% 覆盖，确保核心场景体验好，边缘场景不崩。

能力 2：产品抽象

证据
  • 三卡落盘模型：将科研交互输出抽象为 Evidence/Task/Result 三张卡片，每张有明确 schema。从"用户拿到输出后要做什么"倒推——Evidence 卡存档，Task 卡执行，Result 卡汇报。
  • Concept/Task/Pack 三对象模型：Concept（你在验证什么）驱动 Task（你怎么验证的），Task 结果汇聚成 Pack（你验证出了什么）。覆盖从文献综述到实验执行到论文写作的完整链路。
  • Control Plane / Data Plane 分离：借鉴网络架构思想，将"Agent 如何工作"和"Agent 知道什么"解耦。可以在不改变记忆数据的情况下调整 Agent 行为。

简历表达：设计"Evidence→Task→Result"三卡落盘模型与 Concept/Task/Pack 三对象体系，将科研工作流抽象为可结构化、可追溯、可复用的原子资产。采用 Control Plane / Data Plane 分离架构，实现 Agent 行为规则与记忆数据的解耦，支持独立迭代。

面试追问
  • "三卡落盘和普通结构化输出有什么区别？" → 区别在于 trace 回指。每条结论不是 AI 生成的文本，而是"带证据锚点的断言"。
  • "Concept/Task/Pack 这个抽象怎么来的？" → 从科研工作流倒推。我们没有发明新概念，而是把散落在 Excel/Word/PPT 里的隐式结构显式化了。
  • "Control Plane 和 Data Plane 分离的实际好处？" → Phase 3-5 中多次修改 SOUL.md 的证据标准，用户的 project.md 和实验日志完全不受影响。

能力 3：技术理解

证据
  • LangChain create_agent + LangGraph runtime：明确拒绝旧版 AgentExecutor 和 create_react_agent。v1.1.0 API 消失问题定位后锁定 >=1.1.1。
  • SSE 流式架构：选择 SSE 而非 WebSocket——单向推送足够、HTTP 兼容性好。done 事件在 trace 写入完成后才发送，解决竞态条件。
  • Envelope Schema：Session 消息和 Trace 审计共用同一 JSON 文件，SessionManager 和 TraceWriter 各管各的字段，避免同步问题。
  • 路径安全：Path.relative_to() 做边界检查，禁止 str.startswith()（可被 Unicode 绕过）。
  • 双文件依赖：requirements.txt（范围约束）+ requirements.lock（精确版本），开发灵活、部署可复现。

简历表达：基于 LangChain v1.x create_agent（LangGraph runtime）构建 Agent 编排引擎，SSE 流式推送实现实时工具调用展示。设计 Envelope Schema 统一 Session 消息与 Trace 审计存储，解决读写竞态。实现 Path.relative_to() 路径安全检查防御穿越攻击，双文件依赖策略保证环境可复现。

面试追问
  • "为什么选 SSE 而不是 WebSocket？" → Agent 对话是单向推送场景，SSE 基于 HTTP 天然兼容代理/CDN/负载均衡。WebSocket 在这个场景下是过度设计。
  • "Envelope Schema 会不会有并发写入冲突？" → 不会。单次对话流程串行：Agent 执行完 → 写 messages → 写 traces → 发送 done。
  • "create_agent 和 create_react_agent 的区别？" → create_agent 底层 LangGraph runtime，支持更灵活的状态管理和流式执行。我们需要控制 SSE 事件的精确时序。

能力 4：评测设计

证据
  • Golden Test 剧本：2 条端到端 Demo（DDL 型 10 轮 + 认知流动型 12 轮），每轮有明确输入和期望输出，可作为回归测试基线。
  • 三类闭环测试数据集：从 1.45GB 真实科研资料构建，定义 literature/experiment/writing 三类闭环测试标准，标注 4 类能力标签（context_hit / object_landing / trace_replay / writing_organization）。

  • 8 个单元测试：覆盖 SkillLoader、Chat+WriteFile 流程、System Prompt 契约、5 个核心工具。

简历表达：设计 2 条 Golden Test 剧本作为端到端回归测试基线，定义三类科研闭环的结构化测试标准与 4 类能力标签。每个开发 Phase 配备验收矩阵，8 个单元测试覆盖核心模块契约。

面试追问

Step 4：简历文案

项目名称：Experimental-Research-OpenClaw  |  角色：AI 产品设计 + 后端架构 + Prompt 工程 + 迭代推进  |  6 Phase 迭代（Phase 1-5.3 已完成）

需求洞察

  • 针对材料/化学/环境等实验学科硕博生，识别出长周期科研（180 天）中的三重核心痛点：跨阶段记忆断裂（10+ 次阶段汇报无法快速关联历史数据）、结论与证据脱钩（口头描述无法追溯到原始实验文件）、被导师 challenge 后缺乏结构化排查框架。
  • 通过用户访谈提炼出 2 类典型托管模式（DDL 交付型 / 认知探索型）和 7 个高频科研场景（合成 checklist、实验矩阵、机理证据链审计、表征审计、阶段汇报、写作结构、CSV 作图拟合），每个场景定义明确的上下文读写策略。
  • 明确产品定位差异：不做"更聪明的 ChatGPT"，而是做"带证据链的科研工作台"——输入是实验材料（照片/csv/文献/口头描述），输出是结构化交付物（PPT 大纲/实验 SOP/机理证据链），每条结论区分事实与推断并挂证据回指。

功能设计

  • 设计三层文件记忆架构（Layer1 身份与规则 / Layer2 时间轴推进 / Layer3 原子资产），以 Markdown 文件系统替代向量数据库，实现 180 天实验周期的持久化记忆，用户可直接查看、编辑、追溯所有记忆内容。
  • 抽象 Concept/Task/Pack 三对象模型：Concept 承载研究假设，Task 承载验证过程（Claim + Protocol + Run），Pack 承载阶段交付物（PPT/机理证据链/论文段落），三者形成"假设→验证→交付"的完整闭环。
  • 构建 Control Plane / Data Plane / Trace Plane 三面分离架构：Control Plane（SOUL.md/IDENTITY.md 等）定义 Agent 行为硬约束，Data Plane（三层 memory）存放事实数据，Trace Plane 记录全链路决策过程（读了什么文件/为什么读/是否被裁剪/工具调用输入输出）。
  • 实现 ContextOrchestrator 智能上下文选择（基于意图识别自动匹配文件，按"稳定→变化→本轮相关"排序注入）、PromptBuilder 7-Block 结构化 Prompt 拼接、SkillLoader 渐进式技能披露（菜单摘要注入 Prompt，Agent 自主决策读取完整说明书）。
  • Phase 5.3 完成从全局单例到 WorkspaceRuntimeRegistry 的架构重构，实现多 workspace 运行时隔离（共享 LLM 实例 + 隔离 workspace-scoped 工具），保持 API 向后兼容。

评测体系

  • 设计 2 条 Golden Test 剧本（DDL 交付型 10 轮对话 / 认知探索型 12 轮对话）作为端到端回归测试基线，验证三卡落盘（Evidence/Task/Result）的结构完整性与证据回指准确性。
  • 定义三类科研闭环测试标准（文献闭环 / 实验闭环 / 写作闭环），从 1.45GB 真实科研资料中构建结构化测试数据集，标注 4 类能力标签（上下文命中 / 对象落点 / trace 回放 / 写作组织）。
  • 每个 Phase 配备结构化验收矩阵（PASS/FAIL 状态），8 个单元测试覆盖核心模块契约（SkillLoader 菜单生成、Chat+WriteFile 完整流程、System Prompt 契约、5 个核心工具）。
  • 建立 Phase 开发三件套纪律（dev-plan → dev-log → architecture.html），已知限制显式标注，Bug 修复追加记入对应 Phase 日志。

M08 如果让你重新设计，你会改什么？
考察：产品抽象 + 推进与 debug来源：architecture-summary.md §6 风险分析

避坑：不要说"没什么要改的"。可以说：1) Bootstrap 冷启动体验需优化（当前依赖用户填写 project.md）；2) 意图识别应从关键词匹配升级为 LLM 分类；3) 前端应更早启动，与后端并行。

M09 你怎么处理 LLM 调用失败的情况？
考察：技术理解来源：architecture-summary.md §6.7

避坑：坦诚说 MVP 阶段降级策略比较简单——重试 2 次（间隔 1s/3s），超时 60s，失败后发送 SSE error 事件。没有做复杂熔断。这是有意的取舍——MVP 优先保证核心链路跑通。

M10 Trace 回放在产品层面的价值是什么？
考察：产品抽象来源：PRD §4.3、项目最终实现效果.md

避坑：不要说"方便 debug"。Trace 的产品价值是建立用户信任——科研用户需要理解"AI 为什么给出这个建议"才敢用它的输出去面对导师。

M11 Skills 系统为什么用 Markdown 说明书而不是代码插件？
考察：产品抽象 + 技术理解来源：PRD §三 Skills 范式

避坑：不要只说"更灵活"。三个原因：1) 用户可以自己写 Skill，不需要编程；2) Skill 行为可审计（就是文本）；3) 扩展不需要改代码、不需要重启服务。

M12 你怎么决定哪些信息放 Control Plane、哪些放 Data Plane？
考察：产品抽象来源：PRD §4.4.0

避坑：判断标准是"可变性 + 权威性"。Control Plane 放低频变更、最高权威的硬协议。Data Plane 放允许缓慢演进的事实数据。如果一条信息"与任何记忆冲突时应以它为准"，那它属于 Control Plane。

M13 双文件依赖策略解决什么问题？
考察：技术理解来源：CLAUDE.md、backend/requirements.txt + .lock

避坑：不要只说"锁版本"。两个文件分工——requirements.txt 用范围约束保证开发灵活性，requirements.lock 用精确版本保证部署可复现。解决"在我机器上能跑"问题。

M14 你怎么处理 LangChain v1.1.0 的 create_agent API 消失问题？
考察：推进与 debug来源：architecture-summary.md §6.1

避坑：要说清定位过程——通过 LangChain 论坛发现 v1.1.0 的 __init__.py 导出缺失，锁定 >=1.1.1，并在 CLAUDE.md 中记录决策。要体现排查过程。

M15 这个项目和市面上的 AI 科研助手（如 Elicit、Consensus）有什么区别？
考察：产品抽象来源：PRD §一 核心差异化定位

避坑：不要贬低竞品。区别在定位——Elicit/Consensus 聚焦文献检索和摘要，是"搜索增强"。OpenClaw 聚焦实验全周期管理，是"工作台"。它们解决"找到信息"，我们解决"把信息组织成可交付的东西"。且本地化部署，数据不出本地。

三、高压挑战题（10 题）

H01 你这个项目本质上不就是给 ChatGPT 套了个文件系统吗？
考察：产品抽象来源：ContextOrchestrator + PromptBuilder + TraceWriter 完整链路

避坑：不要急着否认。承认底层确实是 LLM，但关键差异在于"确定性外壳"——ContextOrchestrator 的智能上下文选择、PromptBuilder 的 7-Block 结构化拼接、TraceWriter 的全链路审计。类比：数据库引擎也是"套了个文件系统"，但 B+ 树索引和事务管理才是价值所在。

H02 前端都没做完，你怎么证明这个产品有用？
考察：推进与 debug + 评测设计来源：Golden Test 剧本、Phase 验收矩阵、8 个单元测试

避坑：不要回避。坦诚说前端未完成是事实，但后端核心链路已通过 API 测试和 Golden Test 验证。前端是体验层，不是价值层——价值在于记忆架构和证据链机制，这些已经验证了。

H03 三层记忆听起来很复杂，用户真的需要这么复杂的系统吗？
考察：场景拆解 + 产品抽象来源：PRD §4.1 记忆压力源

避坑：不要为复杂性辩护。要说清"复杂性对用户是透明的"——用户不需要理解三层架构，只需正常对话。ContextOrchestrator 自动选择注入文件，用户感知到的是"系统记住了我 3 个月前的实验"。复杂性在后端，简单性在前端。

H04 你的意图识别只是关键词匹配，这也太简陋了吧？
考察：技术理解 + 推进与 debug来源：architecture-summary.md §6.3

避坑：不要否认简陋。这是有意的 MVP 决策——关键词匹配覆盖 80% 高频场景，失败时安全降级为全量注入。MVP 阶段"不出错"比"更智能"重要。过早引入复杂意图识别是过度工程。

H05 你说"证据回指"，但 LLM 生成的 trace 本身可能是错的，怎么办？
考察：评测设计 + 产品抽象来源：TraceWriter 实现、SOUL.md 证据标准

避坑：要区分两种 trace——系统级 trace（ContextOrchestrator 读了哪些文件、工具调用了什么）是确定性的，由代码生成，不会错。LLM 级 trace（Result 卡中的证据回指）确实可能出错。当前缓解是 SOUL.md 硬约束 + Golden Test 验证结构，但语义准确性需人工审查。

H06 180 天的记忆文件会越来越多，系统性能怎么保证？
考察：技术理解来源：PRD §4.4.4、context_budget.md

避坑：不要说"文件系统很快"。两层保障：1) ContextOrchestrator 按意图选择性读取（阶段汇报只读 time_range 内文件）；2) context_budget.md 定义按层分配的预算策略。但文件数量达数千级别时目录扫描会变慢，后续需加索引或缓存。

H07 你这个项目只有你和另一个人做，怎么证明你的个人贡献？
考察：推进与 debug来源：zly工作文档.md、CLAUDE.md、Phase dev-log

避坑：不要模糊化。要能清晰说出自己负责的部分——比如"我负责产品设计（PRD/TAD）+ 后端架构设计 + Phase 开发流程定义 + Prompt 工程（SOUL.md/IDENTITY.md 等 workspace 模板）"，用 dev-log 中的具体 Step 作为证据。

H08 如果导师说"我不信 AI 的输出"，你的产品怎么应对？
考察：产品抽象来源：Trace Plane 设计、三卡落盘事实/推断分离

避坑：不要说"AI 很准"。要说"我们的设计就是基于'不信 AI'这个前提的"——三卡落盘强制区分事实和推断，每条结论挂证据回指，Trace 可回放完整决策过程。用户说的不是"AI 说的"，而是"基于这个 csv 数据和这次实验记录，得出的结论是..."。系统的价值是"帮你组织证据"，不是"替你思考"。

H09 你的 Skills 系统和 MCP（Model Context Protocol）有什么区别？
考察：技术理解 + 产品抽象来源：PRD §三 Skills 范式

避坑：不要说"差不多"。MCP 是工具协议（定义 AI 如何调用外部工具），Skills 是指令协议（定义 AI 如何组合已有工具完成复杂任务）。Skill 是 Markdown 说明书，教 Agent "先 read_file 读数据，再 python_repl 画图，最后 write_file 保存"。MCP 解决"连接什么工具"，Skills 解决"怎么用这些工具完成科研任务"。

H10 这个项目对你申请 AI PM 岗位的价值是什么？你从中学到了什么？
考察：全局反思来源：整个项目

避坑：不要说"学到了很多技术"。要从 PM 视角总结：1) 学会了从用户痛点倒推产品抽象（三卡落盘是从"用户拿到输出后要做什么"倒推的）；2) 学会了在 AI 产品中平衡"智能"和"确定性"（LLM 越智能越不可控，所以需要 Control Plane 硬约束）；3) 学会了 AI-native 的开发协作模式（CLAUDE.md 驱动开发，人定义规范、AI 按规范执行）。
