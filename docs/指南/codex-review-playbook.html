1. 我背后的审查流程

顺序很重要。顺序错了，容易只看见代码，不看见承诺。

01

定位目标承诺

我先找 PRD、TAD、phase plan、dev log、验收表。核心问题是：这个 phase 到底宣称自己“完成了什么”。如果没有承诺清单，后续审查会变成主观判断。

02

锁定实际入口

我不会只读单个实现文件，而是看调用链。典型顺序是：API 入口 → manager / graph → tool / storage → trace / config。因为很多问题不是“工具本身写错”，而是“接入方式把能力搞偏了”。

03

对账设计与实现

我会逐条对照：文档写了什么，代码真的做了什么，是否只是靠 prompt 约束、注释约束或人工自觉维持。凡是“文档说已实现，代码只是提醒”都属于高价值问题。

04

查边界与反例

我优先查路径绕过、shell/exec、trace 完整性、模板文件污染、状态覆盖、输出截断、错误分支、旧格式兼容。因为这些地方最容易让系统在 demo 能跑，但一上真实场景就失真。

05

验证“验收”是否真的成立

如果日志写“已验证”，我会问：测的是 happy path 还是关键风险点？例如“terminal 能执行 ls”只能证明可用，不能证明安全；“trace 文件写出来了”只能证明落盘，不能证明审计完整。

核心原则

我不是先判断“这段代码好不好”，而是先判断“它有没有兑现文档里的承诺”。这也是为什么你给我的计划写得越清楚，我越容易帮你发现真正的问题。

2. 我怎么做代码审查

重点不是风格，而是风险、回归、失真和伪完成。

边界是否真实存在

典型问题：文档说“受限环境”，代码其实是 shell=True；文档说“隔离环境”，代码其实是原进程 exec。

约束是程序强制还是提示词强制

如果系统关键规则只写在 Prompt 里，而工具/API 不做校验，我会把它判定为“规范存在，机制未实现”。

审计是否足够还原事实

我会看 trace 是否包含完整参数、结果、状态、关联 ID，能否支撑复盘，而不是只留一个“调用过”的痕迹。

实际路径是否与宣称一致

很多 bug 不在函数里，在接入层。比如工具本身安全，但 manager 注册错；或者 trace writer 正确，但 chat 层只传了半截数据。

我最常查的 7 类问题

1
名义安全 vs 实际高权限：黑名单过弱、白名单缺失、同进程执行、路径限制可绕过。
2
验收口径过宽：只验证“能跑”，没有验证“不会错、不会绕、不会丢”。
3
trace 不可信：参数丢失、输出截断、多个 tool call 错配、异常分支不记账。
4
模板文件污染生产逻辑：把 _TEMPLATE、样例文件、README 当成最新记录或真实资产。
5
计划里说“自动化”，代码里其实是人工约定：靠提示词、注释、口头规范维持，而不是系统保证。
6
兼容逻辑会静默丢数据：旧格式迁移时重置、覆盖、吞异常，没有保留原始内容。
7
phase 间承诺冲突：前一份 plan 说 Phase 3 不做，后一份日志又写已实现，但代码根本没跟上。

3. 我怎么检查文档

好的文档不是“内容多”，而是状态清、边界清、验收清。

文档元素 我会检查什么 常见问题
Phase 目标 是否可验证、是否有非目标、是否和前一 phase 对齐 目标过大、边界模糊、把长期目标写成短期承诺
设计方案 是否落到文件、模块、调用链、数据结构 停留在理念层，没有落到代码载体
开发日志 是否区分“已实现”“已建议”“已验证” 把方案讨论写成已完成；把 happy path 写成已验收
验收标准 是否包含负向测试、异常路径、边界条件 只有正向示例，没有反例
风险说明 是否明确单用户/本地/生产的适用边界 默认假设环境可信，但文档不写

文档状态必须分 4 层

可以写成“已实现”

代码已存在，调用链已接通，至少做过一个正向验证和一个关键反向验证。

只能写成“已设计/已建议”

报告提出了方案，或者已经写清路线图，但代码还没改、配置还没落、验收还没跑。

可以写成“已验证”

必须说明验证对象、输入、预期、实际结果。仅有一句“测试通过”是不够的。

必须单列“已知风险”

当你决定暂时不修时，要明确写：风险是什么、当前为什么接受、适用范围是什么、未来何时切换方案。

4. 怎么写更高质量的开发计划

目标不是把文档写长，而是让计划能直接被执行、被验证、被复盘。

推荐结构

1. 背景与目标
2. 明确本 phase 负责什么，不负责什么
3. 关键约束
4. 设计与调用链
5. 文件级改动清单
6. 数据结构 / Prompt / API 变化
7. 验收标准
8. 风险与降级方案
9. 开发日志更新规则

计划里最值得补的 6 个字段

A
非目标：例如“Phase 3 不处理 skills 动态注入，只预留接口”。这能大幅减少后续争议。
B
状态标签：每条结论标明 planned、implemented、verified、risk accepted。
C
反向验收：例如“非法路径应失败”“模板文件不应进入推荐”“多 tool call trace 不应错配”。
D
适用边界：本地单用户可接受，不等于生产可接受。把部署边界写清楚。
E
证据落点：每个核心承诺尽量对应到文件和入口函数，而不是抽象描述。
F
日志回写规则：实施后哪些条目可升级成“已实现”，哪些只能保持“建议方案”。

一个更稳的验收写法

项 不要这样写 更好的写法
工具安全 terminal 能执行命令 terminal 仅允许白名单命令；重定向/管道/子命令必须失败
trace trace 文件能生成 trace 必须包含完整 tool、args、result、timestamp、status；双工具调用不串位
Memory Map 能扫描目录 模板文件和 README 不进入推荐；最近文件排序可解释
溯源 Prompt 里要求写 assets 路径 写入 memory 时校验必须包含 source assets 字段或标准段落

5. 你怎么和我协作会更高效

给我更多“可对账信息”，而不是更多背景故事。

在开始开发前

给我 phase plan、核心约束、非目标、目标文件夹。如果你已经有 dev log，也一并给。我会优先做对账，而不是重复设计。

在开发过程中

把“设计变更”写回文档。不要只改代码不改 plan，也不要只改 plan 不改日志。否则我下一轮审查一定会先花时间校准事实。

在请求 review 时

告诉我你要的是：查安全、查实现偏差、查文档一致性、查回归风险，还是做纯功能验收。目的不同，审查路径会不同。

最有效的协作输入包

1
目标 phase 的计划文档和日志文档。
2
本次改动涉及的代码目录，而不是整个仓库模糊描述。
3
你最担心的 2-3 个问题，例如“trace 对不对”“上传闭环有没有真正落地”。
4
若有“分析报告”，请说明它是建议方案还是已经采纳的决策。
协作心法

你越能把“决策、实现、验证、风险接受”这四件事分开写，我越能快速给你高质量结论。反过来，如果一份文档同时混着方案讨论、实现状态、验收结论，审查成本会明显上升。

6. 直接可用的请求模板

你可以直接复制给我，通常比自由描述更高效。

模板 A：查 phase 实现偏差

检查 phaseX 的开发有什么问题。
范围：docs/xxx-plan.md, docs/xxx-dev-log.md, backend/xxx
重点：
1. 文档承诺和代码实现是否一致
2. 验收是否真的成立
3. 有没有高风险边界问题
4. 按严重程度给 findings

模板 B：让我先做文档对账再开发

先不要改代码。
请先核对以下文档是否自洽：
- docs/phaseX-plan.md
- docs/phaseX-dev-log.md
- docs/related-analysis.md

输出：
1. 冲突点
2. 缺失项
3. 哪些能写成已实现，哪些只能写成建议方案
4. 后续实现顺序

模板 C：让我帮你把计划写得更能执行

请把这份 phase 计划改成可执行版本，但先不要写代码。
要求：
1. 加非目标
2. 加调用链
3. 加负向验收
4. 区分 implemented / verified / risk accepted
5. 保留我现有的目标不变

7. 你的计划自检表

写完 phase plan 或 dev log 后，可以先按这 5 项给自己打分。

1 目标是否可验证，而不是概念化口号
2 每个承诺是否都能落到代码文件和入口
3 是否明确写了非目标和已知风险
4 验收是否包含反向测试与边界场景
5 日志是否区分已实现、已验证、仅建议
达标标准

如果这 5 项里有 4 项以上是明确、可回答的，你的文档就已经足够适合和我高效协作了。如果少于 3 项，通常我会先花时间补结构，而不是直接推进实现。
