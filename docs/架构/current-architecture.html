现在这套架构可以怎么理解

这不是一个“单纯聊天框”，而是一个以 Workspace 文件系统 为中心的研究型 Agent 工作台。前端负责展示和交互，后端负责调度 Agent，Agent 通过 Tools 读写 Memory 与 Assets，最后所有过程都会被 Trace 留痕。

1. 四层总览

先不要看细节，先把系统拆成 4 个盒子。

Frontend

前端是观察窗

  • 三栏 UI：左侧 Layer1/2，中间 Chat + ThoughtChain，右侧 Layer3。
  • 负责消息输入、文件上传、SSE 流式显示、Trace 回放。
  • 它不做决策，主要做可视化和交互承载。
Backend

后端是总调度台

  • `API` 接请求，`ContextOrchestrator` 选上下文，`PromptBuilder` 组 Prompt。
  • `AgentManager` 调用 LangChain `create_agent` 执行任务。
  • `SessionManager` 与 `TraceWriter` 负责持久化和审计。
Tools + Workspace

工具改文件，文件构成记忆

  • Tools 包括 `read_file`、`write_file`、`terminal`、`python_repl`、`fetch_url` 等。
  • Workspace 采用 file-first 设计，控制层、技能快照、三层记忆、资产、审计都在目录里。
  • Agent 的“长期能力”其实落在文件组织方式上。
Trace & Safety

可追溯而不是黑盒

  • 每次对话都会写入 `context_trace/`，保留选了哪些文件、调用了哪些工具。
  • 工具调用经过路径安全、命令黑名单、目录白名单、大小限制。
  • 所以系统既能自动化，又保留工程可控性。

2. 一次对话到底发生了什么

把这个流程记住，你就能读懂大部分模块职责。

接收请求

用户在前端发消息、上传文件，前端调用 `POST /api/chat`。

筛选上下文

`ContextOrchestrator` 扫描 Layer1/2/3，返回当前应该注入的文件和预算。

构建 Prompt

`PromptBuilder` 把控制层文件、技能快照、用户消息拼成完整输入。

Agent 执行

`AgentManager` 开始流式执行，过程中可多次调用 Tools。

读写 Workspace

Tools 读 `memory/`、写 `memory/`，也可能生成 `assets/` 中的图表、数据或素材。

写审计并回放

结束后 `TraceWriter` 落盘，前端再拉取 Trace 详情给用户做回放。

这个链路说明了一个关键点：Agent 不是直接“记住一切”，而是每轮先取一部分文件作为上下文，再通过工具把新的认知重新沉淀回 Workspace。也就是说，它靠“选文件 + 调工具 + 写结果”形成连续性。

3. Workspace 为什么是核心

如果只看一个部分，优先看这里。

Layer 1 · Identity

长期稳定层

定义用户偏好、项目北极星、实验室约束、上下文预算。它回答的是“我们是谁、目标是什么”。

memory/layer1/user.md
memory/layer1/project.md
memory/layer1/lab_context.md
memory/layer1/context_budget.md
Layer 2 · Timeline

时间推进层

记录 180 天总览、阶段、周报、日报、阶段汇报。它回答的是“这件事推进到了哪里”。

memory/layer2/180d_index.md
memory/layer2/phases/ · weeks/ · days/
memory/layer2/stage_reports/
Layer 3 · Atom Notes

原子知识层

把概念、任务、交付物拆成细颗粒度对象，便于复用和溯源。它回答的是“证据和对象具体是什么”。

memory/layer3/concepts/
memory/layer3/tasks/
memory/layer3/packs/

Assets 不是记忆，但它们是证据源

上传文件、实验数据、图表、PPT 素材都放在 `assets/`。Memory 文件不会复制原始大文件，而是嵌入相对路径来保持溯源关系。

assets/uploads/ · 用户原始上传
assets/data/ · 处理中间数据
assets/figures/ · 生成图表
assets/ppt_pack/ · 汇报素材包
理解方式：Memory 负责“结构化认知”，Assets 负责“原始证据和产物”。二者通过路径链接起来，所以用户能从结论一路点回原文件。

4. Skills 和 Tools 是怎么配合的

这个系统把“能力”拆成了两层：技能负责流程，工具负责动作。

Skill Discovery

Agent 先看技能清单

Bootstrap
扫描 `backend/skills/`，生成 `SKILLS_SNAPSHOT.md`。
Prompt 注入
`PromptBuilder` 把快照放进 System Prompt。
决策时机
Agent 根据任务判断是否需要某个 Skill。
Skill Execution

Skill 决定怎么做

read_file
读取完整 `SKILL.md` 说明，而不是只靠简介。
按步骤执行
例如先读周报，再分析素材，再写入 pack。
沉淀输出
结果继续写回 `memory/packs/` 或其他路径。
Tool Surface

Tools 只提供标准动作

读写类
`read_file`、`write_file`、`search_knowledge_base`
执行类
`terminal`、`python_repl`
网络类
`fetch_url`、`web_search`
所以可以把它理解成：Skill = 做事方法论，Tool = 可调用能力接口。前者决定顺序和规则，后者真正完成读、写、算、查。

5. Workspace 的生命周期

这不是一次性目录，而是会演化、归档、克隆的研究容器。

Create

初始化

从 `workspace-templates` 复制基础结构，初始化 memory、assets、trace。

Run

日常运行

每次聊天都经历意图识别、上下文选择、Agent 执行、写回记忆、审计落盘。

Evolve

提炼模式

当重复任务出现时，系统把模式抽成 Skill，并更新 Layer2 记录。

Archive

冻结归档

周期结束时冻结状态，生成 `manifest.json` 便于追踪和交接。

Clone

继承新周期

有选择地继承某些层，再启动下一轮 workspace。

这部分很重要，因为它说明当前架构不是“聊天记录堆积”，而是想做成 可持续演进的研究工作空间。

6. 为什么这套系统是工程化的

因为它给 Agent 上了边界，而不是让它无限制执行。

Path Safety

路径安全

通过 `resolve_safe_path` 做目录边界控制，避免路径穿越。

Command Safety

命令约束

黑名单和允许目录机制把危险命令、危险路径拦在工具层之前。

Auditability

完整留痕

工具调用、上下文选择、输出结果都能在 Trace 中回放，便于复盘和排错。

从架构上看，安全检查层 夹在 Agent 和真实执行动作之间；审计层 则在执行之后留证据。前者防事故，后者防失控。

7. 你可以这样记住它

下面这 3 句话基本就是整套架构的心智模型。

心智模型 1

Workspace 才是“大脑”

模型本身会话性很强，但长期知识被拆进 Layer1/2/3 与 Assets，所以系统记忆不依赖单轮上下文。

心智模型 2

Agent 更像“调度员”

它不直接拥有全部能力，只是决定读哪些文件、调用哪些工具、是否启用某个 Skill。

心智模型 3

Trace 让系统可理解

不是只有结果，而是把中间步骤也留下来，这样用户和开发者都能解释系统到底怎么得出答案。

如果后面你继续扩展这套系统，最值得盯住的主线是：上下文怎么选、技能怎么沉淀、写回什么结构化记忆。这三件事决定它会不会越用越强。
