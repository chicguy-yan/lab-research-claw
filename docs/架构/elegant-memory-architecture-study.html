更优雅的 Memory 与溯源架构学习页

这份页面不是在教你“修 3 个 bug”，而是在训练一种更稳定的架构直觉：当你面对模板过滤、推荐失真、溯源断裂这类问题时，应该优先想到“统一数据模型层”，而不是继续往单点逻辑里塞补丁。

核心结论是：比在 context_orchestrator.py、推荐逻辑、write_file_tool.py 各修一刀更优雅的方式，是引入 Workspace Index + Typed Frontmatter + Provenance Contract。

你想解决的 3 个问题 模板文件污染、推荐误指模板、溯源只靠 prompt 而非程序约束。
更好的统一解法 把目录扫描、推荐、写入校验统一收敛到“结构化内容层”，而不是靠分散 if 维持。
为什么优雅 一份 index 驱动多个能力，一份 schema 约束多个入口，一份 provenance contract 打通 assets 与 memory。
你会形成的直觉 以后遇到类似问题，先想“缺不缺模型层”，再想“要不要补 if”。

1. 这 3 个问题的本质其实是 1 个问题

它们表面不同，根上都指向“系统缺了结构化事实层”。

表面问题 你现在看到的现象 根因
模板过滤失败 _DAY_TEMPLATE.md、_WEEK_TEMPLATE.md 被当真实记录 系统只知道“这是个 md 文件”，不知道“这是 template”
推荐误指模板 “最新阶段汇报”可能指向 _STAGE_REPORT_TEMPLATE.md 推荐逻辑基于文件名排序猜测语义，而不是基于结构化元信息
溯源机制失真 写 memory 只靠 prompt 约束，不带 source assets 也能写成功 写入系统不知道“什么叫有效 memory entry”，缺少写入契约与校验层
一句话抽象

你当前系统把“文件名”和“文本内容”当作唯一事实来源，但你的业务其实已经需要“文档类型、状态、来源、是否模板、是否有效”这类更高阶的结构化事实。

2. 不优雅的修法是什么样

这些修法不是完全没用，而是会把系统慢慢拖向不可维护。

坏方案：分散补丁式修复
1
在扫描函数里加 if name.startswith("_")。
2
在推荐函数里单独写 if "TEMPLATE" not in name。
3
在 prompt 里再强调一次“写入时请带 source assets”。

为什么不优雅

规则散落在多个位置。每多一个入口，就要复制一遍规则。以后 phase5/skills、API、前端编辑器接进来，还得继续复制。

好方案：统一数据模型层
1
先定义 MemoryEntry 的结构和类型字段。
2
用 WorkspaceIndexer 统一生成 catalog。
3
推荐、扫描、写入、校验都围绕 catalog 和 schema 运行。

为什么优雅

你不是在“修 3 个 bug”，而是在补一个架构层。这个层一旦建立，多个问题会同时消失，而且后续能力还能复用它。

3. 更优雅的统一架构

名字可以变，但核心结构建议保留。

Workspace Index

负责扫描 workspace，把“原始文件系统”提升成“结构化 catalog”。它输出的不是文件列表，而是已分类、可过滤、可推荐的内容索引。

Typed Frontmatter

每个 memory 文件携带明确类型和状态：kind、template、status、date、report_id、source_assets。

Provenance Contract

memory 写入必须满足最小溯源契约。没有合格的 source_assets，就不算有效知识沉淀。

Query-Based Recommendation

推荐不靠文件名猜测，而靠 catalog 查询：kind=stage_report AND template=false 这类结构化条件。

最小 frontmatter 例子

---
kind: stage_report
template: false
status: active
report_id: R03
date: 2026-03-10
source_assets:
  - assets/data/exp_005_kobs.csv
  - assets/figures/exp_005_kobs_fit.png
---

# R03 阶段汇报
...
关键设计观念

“模板”不是命名习惯，而是内容类型；“阶段汇报”不是文件前缀，而是业务实体；“已溯源”不是模型自觉，而是系统强制通过的契约。

4. 架构图怎么画才抓住重点

这类系统最适合画“分层图 + 数据流图 + 责任归属图”。

4.1 总体分层图

用户 / 前端 提问、上传 assets、请求汇报、请求分析
→
Agent / API 层 chat、assets upload、tool 调用、prompt 构建
→
Content Intelligence 层 WorkspaceIndexer + Recommendation + Validation
Memory Schema 层 Typed Frontmatter / MemoryEntry / Query Rules
↔
Provenance 层 AssetRegistry + Provenance Contract + Write Gate
↔
Workspace 实体层 memory/*.md / assets/* / context_trace/*.json

4.2 数据流图

上传资产
用户上传文件 → Assets API 保存文件 → AssetRegistry 记录路径 / hash / type → catalog 可见
生成 Memory Map
ContextOrchestrator 不再直接扫目录 → 读取 Workspace Index → 只展示 template=false 的有效条目
推荐文件
根据用户意图查询 catalog，例如 stage_report / task / concept，而不是对裸文件名排序
写入 Memory
write_file 先解析 frontmatter → 校验 kind 与 source_assets → 通过后写入 → 触发 index 更新

4.3 责任归属图

职责 应该由谁负责 不应该由谁负责
判断是不是模板 Schema / Indexer 推荐函数临时猜测
判断是否可推荐 Catalog 查询规则 按文件名逆序排序
判断是否已溯源 Write Gate / Provenance Validator PromptBuilder 文本提醒
决定 memory 文件类型 Frontmatter kind 路径名和文件名约定

5. 每个核心逻辑的优雅点在哪里

优雅不是“看起来高级”，而是规则收敛、职责清晰、扩展自然。

5.1 Workspace Index

它解决什么

把文件系统从“裸文件集合”提升为“可查询内容集合”。以后 Memory Map、推荐、搜索摘要、统计都可以读这一个 index。

反例

如果每个模块都自己 glob("*.md")，那模板过滤、排序规则、可见性规则会在 4 个地方各写一次，迟早漂移。

5.2 Typed Frontmatter

它解决什么

把业务语义写进文件本身。系统不再靠 R03_、_TEMPLATE 这种命名暗号理解内容。

反例

“看到文件名有 TEMPLATE 就跳过”只是一条脆弱约定。以后有人新建 stage_report_template_v2.md 或中文名模板，就会再次漏掉。

5.3 Provenance Contract

它解决什么

把“已溯源”定义成程序可验证的状态，而不是模型口头承诺。没有合格来源，写入直接失败或标为 draft。

反例

如果你只在 prompt 里写“必须包含 assets 路径”，那系统其实无法区分“真正已溯源”和“模型忘写了但依然写成功”。

5.4 Query-Based Recommendation

它解决什么

推荐逻辑基于“内容是什么”，而不是“文件名长什么样”。这是从 heuristic 走向可解释查询的关键一步。

反例

裸排序最常见的问题是：模板排前面、旧文件误判成最新、README 被当正文、示例文件影响推荐。

6. 反例对照：为什么这套架构更优雅

这里用具体“错误设计”训练你的反直觉能力。

反例 1：把模板当文件名问题

错误直觉：模板文件误入推荐，只要在推荐函数排除一下就好。

真正问题：系统从头到尾都不知道“模板是一个业务属性”。

反例 2：把溯源当写作规范

错误直觉：只要 prompt 写得更狠一点，模型就会记得带 source assets。

真正问题：没有写入校验，系统无法拒绝不合格知识。

反例 3：把推荐当字符串游戏

错误直觉：只要正则再精细一点，文件名就能表达业务语义。

真正问题：文件名永远只是弱信号，不能承载完整状态。

三组“坏直觉 → 好直觉”

坏直觉 好直觉
看到 bug 就加 if 先判断是不是缺模型层、缺约束层、缺统一索引层
文件名可以代表类型 类型应该进入 schema，文件名最多是人类可读标签
prompt 能约束一切 关键业务约束必须由程序验证，prompt 只负责引导，不负责保底

7. 下次设计时你该形成的直觉

这是最值得带走的部分。

直觉 1
一个规则被写第二次时，就该想统一层

如果模板过滤同时出现在扫描、推荐、搜索里，就不要继续复制。该抽出 shared index 或 schema 了。

直觉 2
业务实体不要只靠路径表达

memory/timeline/stage_reports/R03.md 是存储位置，不是完整业务定义。业务定义应该在 frontmatter 里。

直觉 3
“有效写入”必须有程序门槛

如果系统无法拒绝不合格写入，那就还没有真正定义这个业务对象。

直觉 4
推荐本质是查询，不是排序技巧

一旦推荐逻辑开始依赖文件名特征、目录顺序、特殊前缀，你就该警觉它会漂。

直觉 5
先设计“失败条件”，再设计 happy path

比如：模板不应可见；无 source assets 不应落盘；非法 kind 不应进入 index。这些失败条件比正向流程更能保护架构。

直觉 6
优雅 = 规则少、复用高、语义清

不是抽象层越多越好，而是让一条规则能在多个能力上复用，而不需要重复描述。

8. 以后你设计类似系统时的检查表

这张表可以直接拿来审自己的方案。

1
我是不是把“类型、状态、来源”这些业务语义只藏在文件名里了？
2
同一条过滤规则是否已经在两个以上模块重复出现？如果是，该抽统一层了。
3
关键业务约束是否只是 prompt 要求，而不是程序硬校验？
4
推荐逻辑是在“按语义查询”，还是在“按文件名猜测”？
5
我的架构图是否单独画出了“索引层”“校验层”“存储层”的责任边界？
6
我有没有明确列出反向验收：模板不可见、无溯源不可写、错误 kind 不可推荐？
最终记忆点

当一个系统开始出现“模板误入、推荐误判、约束失效”这类问题时，通常不是你缺一个更聪明的 if，而是你缺一个把语义收拢起来的结构层。优雅架构最核心的价值，就是把语义放到系统能真正理解和校验的位置上。
