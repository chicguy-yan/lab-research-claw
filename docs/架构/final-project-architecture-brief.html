OpenClaw Research Console 项目架构

这是一个面向研究型 Agent 的本地工作台。核心不是“单次聊天”，而是把 会话、文件系统、研究记忆、技能菜单、工具执行、附件溯源、Trace 审计 放进同一条可持续迭代链路里。

静态前端 三栏控制台，负责会话、文件树、聊天流、附件和 Trace 可视化。
FastAPI 后端 提供 15 个真实可用端点，核心是 /api/chat SSE 流。
Workspace 存储 把记忆、附件、技能、Trace 和会话都统一落到本地文件系统。
一句话定位

把“Agent 对话”升级成“可审计的研究工作流”

用户发起一次问题，系统不只返回文本，还会同步记录工具调用、附件来源、记忆文件变更线索和完整 prompt 载荷， 这样后续可以复盘“读了什么、做了什么、为什么这么回答”。

项目卖点 四层架构 请求闭环 核心模块 当前边界 面试话术

1. 项目卖点

适合在面试里先讲“为什么这个项目不是普通聊天机器人”。

Memory

研究记忆有层次

把长期身份规则、时间轴文档、Concept/Task/Pack 原子笔记拆开，Agent 不再只依赖上下文窗口。

Tooling

Agent 真能操作环境

不是只会“建议做什么”，而是能受控调用 shell、Python、读写文件、抓网页，把动作真正落到 workspace。

Trace

全过程可回放

每轮对话的工具调用和 prompt payload 都写进 envelope，前端可以直接展示这轮审计轨迹。

Assets

附件到知识可溯源

上传文件后会自动分类，后续写入 memory 时可带 source_assets，保证知识文件能追到原始附件。

2. 四层架构

这部分适合画在白板上，结构清楚，面试官容易追问。

Layer 1

Frontend Console

frontend/index.html

负责会话管理、三栏文件树、消息流、附件选择、后端探测、Trace 面板。当前是单文件静态前端。

Layer 2

FastAPI API Layer

backend/api/*.py

负责把聊天、文件系统、Agent 目录、附件等能力暴露成 HTTP 接口，其中 /api/chat 是主链路。

Layer 3

Agent Orchestration

backend/graph/*.py

负责 Memory Map、Skills Snapshot、Prompt 拼接、LangChain Agent 执行和 Trace 落盘。

Layer 4

Workspace File System

backend/.openclaw/workspace-default/

真正的数据底座，承载 memory、assets、skills、context_trace，相当于这个系统的“本地数据库”。

Browser Console ↓ FastAPI Endpoints ↓ Prompt / Skill / Trace Orchestrator ↓ LangChain Agent + 5 Tools ↓ Workspace File System

3. 一次请求如何闭环

这是最适合口述的主流程，控制在 30 秒内能讲完。

Step 1

前端收集上下文

用户选择会话、输入问题、可上传附件，前端还会从 URL hash 取 route 和 prompt_context。

Step 2

后端组装 prompt

生成 Memory Map、Skills Snapshot 和 trusted metadata，拼成完整 system prompt。

Step 3

Agent 执行工具

LangChain Agent 在 5 个工具上做决策，前端实时看到 token、tool_start、tool_end 事件。

Step 4

落盘并回读 Trace

消息、tool traces、prompt payload 一起写回 envelope，前端随后读取同一个 JSON 做回放。

4. 最值得讲的模块

不要把所有文件都讲一遍，讲这 6 个最容易体现工程能力。

先区分这 4 个最容易混淆的角色： app.py ≠ chat.py ≠ SessionManager ≠ AgentManager
app.py 是应用启动和依赖装配入口；chat.py 是单次聊天请求的 HTTP 编排层； SessionManager 负责把会话和审计写到文件；AgentManager 只负责构建并流式执行 Agent。
app.py

系统启动器

backend/app.py

启动时初始化默认 workspace、迁移模板文件、实例化 SessionManager 和 AgentManager，并把 API router 注册到 FastAPI。

chat.py

请求编排器

backend/api/chat.py

收到 POST /api/chat 后，负责生成 prompt、读取历史、消费 Agent 流、保存消息、写 trace、最后发 done 事件。

SessionManager

会话持久化器

backend/graph/session_manager.py

负责创建 session、维护索引、读写 envelope JSON、保存消息、合并连续 assistant 消息。它不懂 prompt，也不执行模型。

AgentManager

Agent 运行器

backend/graph/agent.py

负责基于 system prompt 和工具列表构建 LangChain Agent，并把模型输出转换成 token/tool_start/tool_end 流式事件。

Session

SessionManager

用 envelope schema 把 messages、traces、prompt 合并存储，既能支撑聊天，也能支撑审计。

Prompt

PromptBuilder

把控制平面文件、技能菜单、资产信息、执行约束和 Memory Map 统一注入，避免 Agent 只靠自然语言猜状态。

Skill

SkillLoader

把 system skills 镜像到 workspace，并生成菜单型 snapshot，让 Agent 自主决定要不要读完整 SKILL.md。

Trace

TraceWriter

把工具调用与 prompt payload 持久化，为后续回放、审计和定位问题提供基础。

Assets

附件溯源链路

上传文件自动分类并生成 quick summary，后续写 memory 时可注入 source_assets frontmatter。

Security

path_utils + restricted tools

所有文件路径都通过 workspace 边界检查，shell 工具有限制 cwd、黑名单和超时，不是裸暴露执行环境。

app.py └─ 启动整个服务，装配依赖 chat.py └─ 处理一条聊天请求，把上下游串起来 SessionManager └─ 管会话文件怎么存、怎么读 AgentManager └─ 管 Agent 怎么跑、工具事件怎么流出来

5. 当前边界和诚实说法

这部分很重要，能体现你不是把“规划图”当成“交付图”来讲。

真实边界 1

运行时还是单 workspace

/api/agents 已经能创建多个 workspace，但聊天和文件操作目前仍绑定 workspace-default。

真实边界 2

前端还是单文件实现

当前不是组件化 React/Next.js，而是先用静态控制台把主流程跑通，优先验证交互闭环和后端协议。

真实边界 3

Trace 没有独立 API

前端是通过文件读取接口直接拿 envelope JSON。这样很实用，但后续如果要产品化，建议拆成专门的 Trace 接口。

6. 面试版 30 秒回答

可以直接拿来讲，再按面试官追问展开到模块级。

我做的是一个研究型 Agent 工作台，不是普通聊天机器人。 前端是一个三栏控制台，后端用 FastAPI 提供聊天、文件系统、附件和会话接口；中间层用 PromptBuilder、SkillLoader、 ContextOrchestrator 和 AgentManager，把研究记忆、技能菜单、工具能力和附件信息统一注入给 LangChain Agent。 每轮对话结束后，我会把消息、工具调用和最终 prompt 一起落到本地 envelope JSON，所以这套系统既能执行，也能复盘， 比较适合需要长期迭代的研究场景。
如果被问亮点

重点说可审计性和溯源

一个核心亮点是把 Trace 和 source_assets 接进主链路，让 Agent 输出不是黑箱答案，而是可以回看依据和过程。

如果被问不足

重点说单 workspace 限制

当前最大架构边界是虽然支持创建多个 workspace，但 runtime 还没切换过去。后续如果继续做，会先把 Agent 选择和 workspace 路由打通。
