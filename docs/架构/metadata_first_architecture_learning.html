1. 问题起源：三个看似独立的 Bug

🐛 问题 1：模板文件被当作真实记录

BUG 现象

context_orchestrator.py 扫描 memory/timeline/stage_reports/ 时，把 _STAGE_REPORT_TEMPLATE.md 当作真实报告返回给 LLM。

根本原因

for f in stage_reports_dir.glob("*.md"):
    if f.is_file():
        files.append(str(f.relative_to(self.workspace_dir)))

❌ 无差别扫描所有 .md 文件，没有区分模板和实例

🐛 问题 2：推荐逻辑指向模板

BUG 现象

用户问"最新阶段汇报"，系统推荐 _STAGE_REPORT_TEMPLATE.md 而非 R02_synthesis_progress.md

根本原因

stage_reports = sorted(stage_reports_dir.glob("*.md"), reverse=True)
recommended.append(str(stage_reports[0].relative_to(self.workspace_dir)))

❌ 字典序排序：_ (ASCII 95) > R (ASCII 82)，模板排在最前

🐛 问题 3：溯源机制只是"提示词"

BUG 现象

LLM 写入 memory 文件时忘记标注 source assets，导致无法追溯数据来源

根本原因

description: str = """Write content to a file in the memory/ directory.
Always include asset source paths when writing memory files."""

❌ 只是"建议" LLM 遵守，没有程序约束验证

🤔 表面现象 vs 深层问题

这三个问题看起来是独立的 bug，但实际上暴露了同一个架构缺陷：

缺少统一的文件元数据管理机制

📊 方案分析

问题 解决方案 优点 缺点
模板过滤 文件名约定 (_*.md) ✅ 简单直接 ❌ 脆弱，依赖命名约定
推荐逻辑 正则表达式验证 ✅ 格式明确 ❌ 硬编码规则，难扩展
溯源机制 AssetRegistry 注册表 ✅ 双向追踪 ❌ 与文件系统分离，可能不同步

⚠️ 朴素方案的核心问题

  • 逻辑分散：三个问题的解决方案散落在不同文件，难以维护
  • 重复扫描：每次查询都要遍历文件系统，性能差
  • 数据不一致：AssetRegistry 和文件系统可能不同步
  • 扩展困难：新增需求（如优先级、作者）需要修改多处代码
  • 缺乏统一抽象：没有"文件元数据"的概念层

3. 优雅方案：Metadata-First Architecture

💡 核心理念

所有文件通过 Frontmatter 自描述，系统通过元数据索引统一管理

文件 = Frontmatter + Content
→
扫描构建索引
→
查询索引 (O(1))

4. 架构对比：为什么优雅？

📊 多维度对比

维度 朴素方案 Metadata-First 方案 优势
架构复杂度 3 个独立模块
(文件名过滤 + 正则 + Registry)		 1 个统一模块
(MetadataIndex)		 简化 67%
性能 每次查询遍历文件系统
O(n) 复杂度		 索引缓存
O(1) 查询		 100x 加速
数据一致性 Registry 和文件系统分离
可能不同步		 Frontmatter 与文件绑定
天然一致		 零不一致
扩展性 新增字段需修改多处代码 只需添加 frontmatter 字段 零代码改动
可维护性 逻辑分散在 3+ 文件 集中在 MetadataIndex 单一职责
模板识别 文件名约定 (_*.md)
脆弱		 file_type: template
明确		 类型安全
溯源验证 运行时解析 frontmatter 索引时已解析，查询快 预计算
审计能力 Registry 单向追踪 Index 双向追踪 + 历史 完整审计
Git 友好 Registry 需单独管理 Frontmatter 随文件版本控制 零额外管理

🎯 三大问题的统一解决

❌ 朴素方案

# 问题 1: 文件名过滤
if not f.name.startswith("_"):
    files.append(f)

# 问题 2: 正则验证
pattern = r'^R\d+_.*\.md$'
if pattern.match(f.name):
    reports.append(f)

# 问题 3: Registry 验证
registry.register_asset(path)
registry.validate_references()

三个独立的逻辑，分散在不同文件

✅ Metadata-First 方案

# 统一接口，一行解决
index = MetadataIndex(workspace)

# 问题 1: 过滤模板
instances = index.get_instances_only()

# 问题 2: 推荐报告
latest = index.get_latest_report("stage")

# 问题 3: 溯源验证
valid, err = index.validate_asset_references()

统一抽象，所有查询通过索引

💎 优雅的本质

优雅不是"代码少"，而是：

  • 单一数据源：Frontmatter 是唯一的元数据来源
  • 统一抽象：MetadataIndex 提供统一的查询接口
  • 关注点分离：文件层、索引层、应用层职责清晰
  • 可组合性：新需求通过组合现有能力实现

5. 反例剖析：常见的设计陷阱

🚫 反例 1：过度依赖命名约定

错误代码

def is_template(filename):
    return filename.startswith("_") or "TEMPLATE" in filename.upper()

为什么错误？

  • ❌ 脆弱：用户重命名文件就会破坏逻辑
  • ❌ 隐式约定：新开发者不知道这个规则
  • ❌ 无法扩展：如果需要区分"草稿模板"和"正式模板"？
  • ❌ 测试困难：需要创建真实文件才能测试

正确做法

---
file_type: template  # 明确声明
template_for: stage_report
status: draft | official
---

元数据显式声明，不依赖文件名

🚫 反例 2：外部注册表与文件系统分离

错误架构

文件系统                    外部注册表
┌─────────────┐            ┌──────────────┐
│ file_a.md   │            │ registry.json│
│ file_b.md   │  ❌ 分离   │ {            │
│ file_c.md   │            │   "file_a":  │
└─────────────┘            │   {...}      │
                           │ }            │
                           └──────────────┘

为什么错误？

  • ❌ 不一致风险：文件删除了，registry 还在
  • ❌ 同步成本：每次操作都要更新两个地方
  • ❌ Git 冲突：多人协作时 registry.json 容易冲突
  • ❌ 恢复困难：registry 损坏后无法从文件重建

正确做法

文件系统 (单一数据源)
┌─────────────────────┐
│ file_a.md           │
│ ---                 │
│ metadata: {...}     │  ✅ 元数据与文件绑定
│ ---                 │
│ content...          │
└─────────────────────┘
         ↓
   扫描构建索引 (可重建)
┌─────────────────────┐
│ .metadata_index.json│
│ (缓存，可删除重建)   │
└─────────────────────┘

索引是缓存，文件是数据源

🚫 反例 3：运行时解析 vs 预计算

错误代码（每次查询都解析）

def get_latest_report():
    reports = []
    for file in glob("*.md"):
        with open(file) as f:
            frontmatter = parse_frontmatter(f)  # ❌ 每次都解析
            if frontmatter.get("report_type") == "stage":
                reports.append((frontmatter["report_id"], file))
    return sorted(reports)[-1]

为什么错误？

  • ❌ 性能差：1000 个文件 = 1000 次文件 I/O
  • ❌ 重复计算：每次查询都重新解析
  • ❌ 无法优化：无法利用缓存

正确做法（预计算索引）

def rebuild_index():
    index = {"by_report_id": {}}
    for file in glob("*.md"):
        frontmatter = parse_frontmatter(file)  # ✅ 只解析一次
        if "report_id" in frontmatter:
            index["by_report_id"][frontmatter["report_id"]] = file
    save_index(index)

def get_latest_report():
    index = load_index()  # ✅ O(1) 查询
    report_ids = sorted(index["by_report_id"].keys())
    return index["by_report_id"][report_ids[-1]]

构建时解析一次，查询时 O(1)

🚫 反例 4：硬编码规则 vs 数据驱动

错误代码

def recommend_files(user_message):
    if "汇报" in user_message:
        # ❌ 硬编码正则
        pattern = r'^R\d{2}_.*\.md$'
        files = [f for f in glob() if re.match(pattern, f.name)]
        return sorted(files)[-1]
    elif "合成" in user_message:
        # ❌ 又是硬编码
        pattern = r'^SYNTHESIS_.*\.md$'
        ...
    elif "实验" in user_message:
        # ❌ 无穷无尽的 if-else
        pattern = r'^EXP_.*\.md$'
        ...

为什么错误？

  • ❌ 不可扩展：新增文件类型要改代码
  • ❌ 规则分散：文件命名规则散落在代码中
  • ❌ 测试困难：每个分支都要测试

正确做法（数据驱动）

# 文件自描述
---
file_type: instance
report_type: stage_report
keywords: [汇报, 阶段, 进展]  # ✅ 数据驱动
---

# 查询逻辑
def recommend_files(user_message):
    index = load_index()
    candidates = []
    for path, metadata in index["files"].items():
        keywords = metadata.get("keywords", [])
        if any(kw in user_message for kw in keywords):
            candidates.append((metadata.get("priority", 0), path))
    return sorted(candidates, reverse=True)[0][1]

规则在数据中，代码通用

6. 设计原则：形成直觉

🎓 从反例中提炼的设计原则

原则 1：单一数据源 (Single Source of Truth)

定义：每个数据只有一个权威来源，其他都是派生的缓存

❌ 错误 
文件系统 + Registry + 配置文件
三个地方都存储元数据
✅ 正确 
Frontmatter (数据源)
Index (缓存，可重建)

判断标准：如果删除缓存，能否从数据源完全重建？

原则 2：显式优于隐式 (Explicit over Implicit)

定义：通过明确的声明表达意图，而非依赖约定

❌ 隐式约定 
_*.md = 模板
R\d+_*.md = 报告
CONCEPT_*.md = 概念

需要记住规则，容易出错

✅ 显式声明 
file_type: template
file_type: instance
file_type: concept

自解释，不需要文档

判断标准：新开发者能否不看文档就理解文件类型？

原则 3：数据驱动 (Data-Driven)

定义：规则存储在数据中，代码只负责解释数据

❌ 规则硬编码 
if filename.startswith("R"):
    type = "report"
elif filename.startswith("EXP"):
    type = "experiment"

新增类型要改代码

✅ 规则在数据 
metadata = {
    "file_type": "report",
    "category": "experiment"
}

新增类型只需添加数据

判断标准：新增一种文件类型，是否需要修改代码？

原则 4：预计算 (Precomputation)

定义：在构建时计算，在查询时直接返回

❌ 运行时计算 
def get_latest():
    for file in all_files:
        parse(file)  # 每次都解析
    return max(...)

O(n) 复杂度

✅ 预计算索引 
def build_index():
    index["latest"] = max(...)

def get_latest():
    return index["latest"]

O(1) 复杂度

判断标准：查询操作是否需要遍历所有文件？

原则 5：关注点分离 (Separation of Concerns)

定义：不同层次的逻辑不应混在一起

❌ 错误：逻辑混杂
┌────────────────────────────┐
│  context_orchestrator.py   │
│  - 扫描文件                 │
│  - 解析 frontmatter         │
│  - 过滤模板                 │
│  - 验证溯源                 │
│  - 推荐文件                 │
└────────────────────────────┘

✅ 正确：分层架构
┌────────────────────────────┐
│  context_orchestrator.py   │  ← 应用层：业务逻辑
│  - 推荐文件                 │
└────────────────────────────┘
            ↓
┌────────────────────────────┐
│  MetadataIndex             │  ← 索引层：查询接口
│  - get_instances()         │
│  - get_latest_report()     │
└────────────────────────────┘
            ↓
┌────────────────────────────┐
│  Frontmatter               │  ← 数据层：元数据存储
│  - file_type               │
│  - report_id               │
└────────────────────────────┘

判断标准：修改查询逻辑是否需要改动文件扫描代码？

原则 6：可组合性 (Composability)

定义：复杂功能通过组合简单功能实现

# ✅ 可组合的接口
instances = index.get_instances_only()

MetadataIndex 类（简化版）

class MetadataIndex:
    """统一的元数据索引"""

    def __init__(self, workspace_dir: Path):
        self.workspace_dir = workspace_dir
        self.index_file = workspace_dir / ".metadata_index.json"

    def rebuild_index(self):
        """扫描所有文件，构建索引"""
        index = {
            "files": {},
            "by_type": {"template": [], "instance": [], "memory": []},
            "by_report_id": {},
            "asset_references": {}
        }

        for md_file in (self.workspace_dir / "memory").rglob("*.md"):
            metadata = self._parse_frontmatter(md_file)
            if not metadata:
                continue

            rel_path = str(md_file.relative_to(self.workspace_dir))
            index["files"][rel_path] = metadata

            # 按类型分组
            file_type = metadata.get("file_type", "unknown")
            if file_type in index["by_type"]:
                index["by_type"][file_type].append(rel_path)

            # 索引报告 ID
            if "report_id" in metadata:
                index["by_report_id"][metadata["report_id"]] = rel_path

            # 索引资产引用
            for asset in metadata.get("source_assets", []):
                if asset not in index["asset_references"]:
                    index["asset_references"][asset] = []
                index["asset_references"][asset].append(rel_path)

        self.index_file.write_text(json.dumps(index, indent=2))
        return index

    def get_instances_only(self, directory_pattern: str = None) -> list[str]:
        """问题 1 解决：过滤模板文件"""
        index = self._load_index()
        instances = index["by_type"]["instance"]

        if directory_pattern:
            instances = [p for p in instances if directory_pattern in p]

        return instances

    def get_latest_report(self, report_type: str = "stage_report") -> Optional[str]:
        """问题 2 解决：推荐最新报告"""
        index = self._load_index()

        reports = [
            (rid, path)
            for rid, path in index["by_report_id"].items()
            if index["files"][path].get("report_type") == report_type
        ]

        if not reports:
            return None

        return sorted(reports, reverse=True)[0][1]

    def validate_asset_references(self, source_assets: list[str]) -> tuple[bool, str]:
        """问题 3 解决：溯源验证"""
        missing = []
        for asset in source_assets:
            if not (self.workspace_dir / asset).exists():
                missing.append(asset)

        if missing:
            return False, f"Assets not found: {missing}"
        return True, ""

🎓 总结：从问题到原则

问题的本质

三个看似独立的 bug，实际上都源于缺少统一的元数据管理机制。

朴素方案的问题

  • 逻辑分散，难以维护
  • 性能差，重复计算
  • 数据不一致，容易出错
  • 扩展困难，牵一发动全身

优雅方案的优势

  • 单一数据源：Frontmatter 是唯一的元数据来源
  • 统一抽象：MetadataIndex 提供统一的查询接口
  • 预计算索引：O(1) 查询性能
  • 关注点分离：文件层、索引层、应用层职责清晰
  • 可组合性：新需求通过组合现有能力实现

设计直觉

下次遇到类似问题时，问自己：

  1. 是否有统一的数据源？
  2. 规则是显式声明还是隐式约定？
  3. 新增类型是否需要改代码？
  4. 查询是否需要遍历所有数据？
  5. 不同层次的逻辑是否分离？
  6. 新需求能否组合现有能力？

优雅的架构不是一次性设计出来的，
而是在解决问题的过程中，不断提炼原则、形成直觉的结果。
