开发反思：从功能缺口推到 Bootstrap

这份复盘来源于 docs/phase5.3-dev-plan.md 的推进过程。 它记录的不是“改了什么”，而是问题如何一步步从前端缺口上升为 runtime、workspace 语义和 bootstrap 生命周期问题。

4 层 功能缺口 → runtime 绑定 → workspace 定义 → bootstrap 入口
2 条线 技术作用域和产品语义作用域被明确拆开
1 个控制点 最终把很多问题统一收敛到 BOOTSTRAP 的职责重定义

核心判断

对开发者最有价值的，不是想到某个新功能，而是能从局部 bug 一路追到真正的系统控制点， 再把范围收回来，决定“这期先做哪一层”。

思维路径

来自 Phase 5.3

1. 先追问概念边界

起点不是直接实现 Agent / Workspace 切换，而是先把 runtime、 workspace、agent 这些词的含义问清楚。 这一步让问题从“功能缺少一个按钮”升级为“概念可能混用”。

2. 从表面缺口追到运行时绑定

真正的卡点不是 /api/agents 只能建目录，而是整个系统在启动时就把 SessionManager 和 AgentManager 固定绑定到了 workspace-default。 也就是说，问题先被识别为 runtime routing 问题，而不是 UI 问题。

3. 再追到 workspace 的双重含义

对照官方 OpenClaw 之后，意识到官方的 workspace 更偏技术工作范围， 而当前项目里的 workspace 同时承担技术隔离单元和研究语义容器两层含义。 这一刀把“技术作用域”和“产品语义作用域”拆开了。

4. 最后把问题前移到 bootstrap

当 workspace 不再被默认理解为完整 180 天主线时，系统就不能靠模板硬编码其语义边界。 于是 BOOTSTRAP 的职责被上升成： 用“用户意图 + 初始材料”共同定义 workspace 的最小边界，再生成与之相称的初始化骨架。

5. 但阶段边界没有失控

即使问题已经推到了 bootstrap，最终仍把 Phase 5.3 收敛回 workspace runtime routing + naming， 并把 bootstrap 明确成下一层生命周期能力。这一步说明抽象能力和范围控制同时存在。

值得学习

开发者视角

先定义问题，再定义方案

不是一上来改接口，而是先问“系统里这些词到底是什么意思”。 对复杂系统来说，概念清晰度通常比代码实现速度更重要。

识别真正的控制点

表面看是前端不能切 workspace，深层是 runtime 固定绑定，继续往上是 workspace 的语义边界不应由模板默认。问题被一步步收敛到更高层的入口。

能把很多问题收成一个入口

最终很多分散问题都统一到了 BOOTSTRAP： 它不只是填模板，而是初始化协议和边界识别器。

值得警惕

架构副作用

1. 容易过早升维

抽象能力强的人，很容易把本期问题一路推到下一层模型问题。 这次的好处是最终收住了：5.3 先只做 runtime routing，不把 bootstrap 全吞进去。

2. 文档可能先于实现膨胀

一旦进入 scope / plan / summary 这些中间概念，协议会自然长大。 开发者要持续追问：这些结构是执行必须，还是分析时有帮助但不一定要落盘。

一个典型提醒

“想清楚了”不等于“现在就该做”。好的架构推进不是把所有正确的事一次做完， 而是把正确的事分层做完。

对开发者的启发

可迁移的方法

区分技术作用域和产品语义作用域

同一个对象常常同时承担两层含义。只要这两层没拆开，系统就会出现“代码能跑，但产品语义混乱”的情况。

状态流比字段更重要

最后收敛到 provision → bootstrap → active，说明真正重要的是生命周期，而不是先堆更多字段。

模板不应该绑架产品模型

旧模板默认 workspace 是完整科研主线，这其实是模板在定义产品。 正确顺序应该是产品先定义边界，再让模板服从边界。

一句话总结

Source: Phase 5.3

这条思维路径最值得学习的地方，不是“想到 bootstrap”，而是能从一个功能缺口一路追到概念定义、 生命周期入口和系统控制点，最后还能把阶段范围收回来。
