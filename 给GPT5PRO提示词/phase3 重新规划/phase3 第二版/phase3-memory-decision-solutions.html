Phase 3 Memory Decision 方案对比

Experimental-Research-OpenClaw — 三种 memory_decision 产出方案的详细分析

⚠️ 核心问题

memory_decision 是 Phase 3 验收的关键字段，但当前设计中没有任何模块负责产出它：

  • PromptBuilder：明确声明"不负责 memory 决策"
  • TraceWriter：只负责"接收"并写入，不负责生成
  • ContextOrchestrator：只负责上下文选择
  • 新增文件列表：没有独立的决策模块

这导致 api/chat.py 的集成流程中，Step 4 (LLM 调用) 到 Step 6 (TraceWriter) 之间存在责任链断裂。

三种解决方案

方案 1：独立规则引擎
短期推荐
📍 决策时机

在 LLM 调用之前，基于用户消息和 intent hint

🔧 实现方式

新增独立模块 MemoryDecisionEngine，在 api/chat.py 的 Step 4-5 之间调用

💻 代码示例
# Step 4.5: 规则引擎决策 decision_engine = MemoryDecisionEngine() memory_decision = decision_engine.decide( message=message, intent_hint=context_result.intent_hint, workspace_state=workspace_state ) # 返回示例 { "action": "write", "target_layer": "Layer3", "target_type": "Task", "target_path": "memory/tasks/TASK_exp_005.md", "reason": "检测到实验关键词，建议写入实验任务" }
🎯 决策逻辑
  • 关键词匹配：["实验", "XRD", "SEM"] → write Task
  • Intent hint：experiment_closure → write Task
  • Intent hint：stage_progress → write Timeline
  • Intent hint：general_consult → skip
✅ 优点
  • 实现简单，纯代码逻辑
  • 完全确定性，可控性强
  • 符合 phase3-dev-plan 的降级方案
  • 可以快速闭环验收
❌ 缺点
  • 准确性较低（盲猜）
  • 无法基于 LLM 实际回答内容
  • 规则维护成本高
  • 不符合"LLM 软约束下自进化"理念
方案 2：ContextOrchestrator 扩展
短期备选
📍 决策时机

在 LLM 调用之前，与上下文选择同步完成

🔧 实现方式

扩展 ContextOrchestrator.select_context()，在返回的 ContextResult 中新增 memory_suggestion 字段

💻 代码示例
# ContextResult 新增字段 @dataclass class ContextResult: intent_hint: str context_files: list[ContextFile] budget_report: dict control_context: list[str] memory_suggestion: dict # ← 新增 # ContextOrchestrator 内部逻辑 def select_context(self, message, ...): intent_hint = self._detect_intent(message) context_files = self._select_files(intent_hint) # 基于 intent 产出 memory 建议 memory_suggestion = self._suggest_memory_action( intent_hint, message ) return ContextResult(..., memory_suggestion)
✅ 优点
  • 不需要新增模块
  • 与 intent 识别逻辑复用
  • 职责内聚（上下文+决策）
❌ 缺点
  • ContextOrchestrator 职责过重
  • 仍然是 LLM 调用前的盲猜
  • 准确性与方案 1 相同
方案 3：LLM 结构化输出
长期目标
📍 决策时机

在 LLM 调用之后，从 LLM 输出中解析

🔧 实现方式

修改 system prompt，要求 LLM 在回答末尾输出结构化的 <memory_decision> 标签

💻 Prompt 示例
# System Prompt 新增部分 在回答用户后，你必须在末尾输出 memory 决策： <memory_decision> { "action": "write" | "skip", "target_layer": "Layer1" | "Layer2" | "Layer3" | null, "target_path": "memory/tasks/TASK_exp_005.md" | null, "reason": "本轮完成了 XRD 表征，需要更新实验任务记录" } </memory_decision>
💻 后端处理
# Step 4: LLM 调用 response_text = await agent.astream(...) # Step 4.5: 解析 memory_decision memory_decision = extract_memory_decision(response_text) clean_response = remove_memory_decision_tag(response_text) # Step 5: 保存消息（清理后的回答） session_manager.save_message(clean_response) # Step 6: 写入 trace（含 memory_decision） trace_writer.write_trace(..., memory_decision)
✅ 优点
  • 准确性最高：基于实际回答内容
  • 符合 phase3-index 原始设计意图
  • 符合"LLM 软约束下自进化"理念
  • 为 Phase 4+ 工具调用打基础
❌ 缺点
  • 需要 prompt 工程
  • LLM 可能不遵守格式
  • 需要解析逻辑（正则/JSON）
  • 实现复杂度中等

集成流程对比

方案 1 & 2：规则引擎（LLM 调用前）

Step 1. SessionManager.load_session_for_agent()
Step 2. ContextOrchestrator.select_context()
Step 3. PromptBuilder.build()
Step 4. MemoryDecisionEngine.decide() ← 新增（方案 1）
或 ContextResult.memory_suggestion ← 扩展（方案 2）
Step 5. AgentManager.astream() — LLM 调用
Step 6. SessionManager.save_message()
Step 7. TraceWriter.write_trace(memory_decision)
Step 8. yield SSE done

方案 3：LLM 结构化输出（LLM 调用后）

Step 1. SessionManager.load_session_for_agent()
Step 2. ContextOrchestrator.select_context()
Step 3. PromptBuilder.build() — 注入 memory_decision 要求
Step 4. AgentManager.astream() — LLM 调用
Step 5. extract_memory_decision(response) ← 新增解析逻辑
Step 5.5. remove_memory_decision_tag(response) ← 清理标签
Step 6. SessionManager.save_message(clean_response)
Step 7. TraceWriter.write_trace(memory_decision)
Step 8. yield SSE done

推荐路径

🎯 短期（Phase 3 验收）

采用方案 1：独立规则引擎

  • 新增 graph/memory_decision_engine.py
  • 在 api/chat.py 的 Step 4-5 之间调用
  • 基于 intent hint 和关键词匹配做决策
  • 快速闭环，满足验收标准

🚀 长期（Phase 4+）

迁移到方案 3：LLM 结构化输出

  • 修改 PromptBuilder，注入 memory_decision 要求
  • 实现 extract_memory_decision() 解析函数
  • 逐步替换规则引擎
  • 为工具调用和复杂决策打基础

✅ Phase 3 最小可行方案

新增文件：backend/graph/memory_decision_engine.py

class MemoryDecisionEngine: def decide( self, message: str, intent_hint: str, workspace_state: dict ) -> dict: """ 基于规则判断 memory 写入决策 返回: { "action": "write" | "skip", "target_layer": "Layer1" | "Layer2" | "Layer3" | null, "target_path": str | null, "reason": str } """ # 规则 1: intent_hint 映射 if intent_hint == "experiment_closure": return { "action": "write", "target_layer": "Layer3", "target_type": "Task", "target_path": self._generate_task_path(), "reason": "实验闭环，写入 Task" } # 规则 2: 关键词匹配 if any(kw in message for kw in ["阶段汇报", "进度"]): return { "action": "write", "target_layer": "Layer2", "target_path": "memory/timeline/...", "reason": "阶段进度，写入 Timeline" } # 规则 3: 默认 skip return { "action": "skip", "target_layer": null, "target_path": null, "reason": "通用咨询，无需写入 memory" }

修改文件：backend/api/chat.py

# 新增 import from graph.memory_decision_engine import MemoryDecisionEngine # 在 chat 函数中 context_result = context_orchestrator.select_context(...) system_prompt = prompt_builder.build(...) # ← 新增：Step 4.5 decision_engine = MemoryDecisionEngine() memory_decision = decision_engine.decide( message=message, intent_hint=context_result.intent_hint, workspace_state={...} ) # LLM 调用 async for chunk in agent_manager.astream(...): yield chunk # 写入 trace（传入 memory_decision） trace = trace_writer.write_trace( ..., memory_decision=memory_decision )
