Phase 3 方案 3 实施路线图

LLM 结构化输出方案 — 让模型在回答时同步产出 memory 决策

🎯 核心理念

方案 3 采用 LLM 结构化输出，让模型在生成回答的同时，输出结构化的 memory_decision 标签。 这种方式符合 phase3-index.md 的原始设计意图："Step 4. 生成回答与 memory 决策"， 让 LLM 基于实际生成的回答内容做出准确的 memory 写入决策，而非在调用前盲猜。

与原设计的对齐：phase3-index.md § 5 明确要求"模型生成回答，同时形成本轮的 memory 决策"， 方案 3 通过 prompt 工程实现了这一设计，是三种方案中唯一完全符合原始架构意图的方案。

📋 实施概览

本路线图分为 5 个 Stage，从 Prompt 设计到降级策略，涵盖完整的实施流程：

  • Stage 1: Prompt 工程 — 设计 memory_decision 输出格式
  • Stage 2: 解析器实现 — 实现 extract_memory_decision()
  • Stage 3: 集成修改 — 修改 PromptBuilder 和 chat.py
  • Stage 4: 验证测试 — 端到端测试
  • Stage 5: 降级策略 — LLM 不遵守格式时的 fallback

💻 Prompt 设计

在 PromptBuilder 的 system prompt 中新增 Block 7（Memory Decision 指令）：

# Block 7: Memory Decision Protocol 在回答用户后，你必须在回答末尾输出 memory 决策标签： <memory_decision> { "action": "write" | "skip", "target_layer": "Layer1" | "Layer2" | "Layer3" | null, "target_type": "Task" | "Pack" | "Concept" | "Timeline" | null, "target_path": "memory/tasks/TASK_xxx.md" | null, "reason": "简短说明为什么写入或跳过" } </memory_decision> ## 决策规则 ### 写入 Layer1 (identity/) 仅在出现稳定、长期影响后续判断的内容时： - 新的主线判据 - 新的实验室硬约束 - 新的用户长期偏好 ### 写入 Layer2 (timeline/) 仅在涉及时间推进信息时： - 今天做了什么 → "memory/timeline/days/YYYY-MM-DD.md" - 本周风险 → "memory/timeline/weeks/WEEK_XX.md" - 阶段汇报索引更新 → "memory/timeline/stage_reports/..." ### 写入 Layer3 (concepts/ + tasks/ + packs/) - Task: 新的可验证工作单元（新 claim、新 protocol、新实验 run） - Pack: 交付组织（阶段汇报、机理证据链、写作目录树） - Concept: 明显出现新研究主线时（优先挂已有 Concept） ### Skip - 通用咨询、信息查询、无需沉淀的对话 - 信息不足，无法形成有效 memory 更新 ## 示例 # 示例 1: 实验闭环 用户："XRD 数据显示 Co(IV) 特征峰在 2θ=31.2°" 你的回答：根据 XRD 数据...（正常回答） <memory_decision> { "action": "write", "target_layer": "Layer3", "target_type": "Task", "target_path": "memory/tasks/TASK_exp_005.md", "reason": "XRD 表征完成，需要更新实验任务记录" } </memory_decision> # 示例 2: 通用咨询 用户："什么是 Fenton 反应？" 你的回答：Fenton 反应是...（正常回答） <memory_decision> { "action": "skip", "target_layer": null, "target_type": null, "target_path": null, "reason": "通用知识咨询，无需写入 memory" } </memory_decision>

✅ 验证方式

  • 手动测试：用 LLM playground 测试 prompt，确认模型能正确输出标签
  • 格式检查：确认 JSON 格式正确，字段完整
  • 边界测试：测试 skip 场景、write 场景、信息不足场景
⚠️ 潜在风险
  • LLM 不遵守格式：可能输出不完整的 JSON 或忘记输出标签
  • 中文干扰：reason 字段使用中文可能影响 JSON 解析
  • 缓解措施：在 Stage 2 实现健壮的解析器 + Stage 5 降级策略
Stage 2: 解析器实现
关键阶段

🎯 目标

实现 extract_memory_decision() 函数，从 LLM 输出中提取并解析 memory_decision 标签。

📁 涉及文件

backend/graph/memory_decision_parser.py

💻 解析器实现

import re import json from typing import Optional def extract_memory_decision(response_text: str) -> Optional[dict]: """ 从 LLM 输出中提取 memory_decision 标签 返回: - 成功: {"action": "write"|"skip", ...} - 失败: None """ # 正则提取 <memory_decision>...</memory_decision> pattern = r'<memory_decision>\s*(\{.*?\})\s*</memory_decision>' match = re.search(pattern, response_text, re.DOTALL) if not match: return None json_str = match.group(1) try: decision = json.loads(json_str) # 验证必需字段 required_fields = ["action", "target_layer", "target_path", "reason"] if not all(field in decision for field in required_fields): return None # 验证 action 值 if decision["action"] not in ["write", "skip"]: return None return decision except json.JSONDecodeError: return None def remove_memory_decision_tag(response_text: str) -> str: """ 从 LLM 输出中移除 memory_decision 标签，返回干净的回答 """ pattern = r'<memory_decision>.*?</memory_decision>' cleaned = re.sub(pattern, '', response_text, flags=re.DOTALL) return cleaned.strip() def get_fallback_decision() -> dict: """ 降级决策：LLM 未输出或解析失败时的默认值 """ return { "action": "skip", "target_layer": None, "target_type": None, "target_path": None, "reason": "LLM 未输出 memory_decision，降级为 skip" }

✅ 验证方式

  • 单元测试：测试正常 JSON、缺失字段、格式错误、无标签等场景
  • 边界测试：测试中文 reason、嵌套 JSON、多个标签等
  • 性能测试：确认正则匹配不会成为瓶颈
✅ 设计亮点
  • 健壮性：解析失败返回 None，不抛异常
  • 降级策略：提供 get_fallback_decision() 保证流程不中断
  • 清理函数：remove_memory_decision_tag() 确保用户看不到内部标签

# backend/api/chat.py from graph.memory_decision_parser import ( extract_memory_decision, remove_memory_decision_tag, get_fallback_decision ) async def chat(request: ChatRequest): # Step 1-3: 原有逻辑 session = session_manager.load_session_for_agent(session_id) context_result = context_orchestrator.select_context(message) system_prompt, user_prompt = prompt_builder.build(context_result, message) # Step 4: LLM 调用（收集完整输出） full_response = "" async for chunk in agent_manager.astream(user_prompt, history, system_prompt): if chunk.get("type") == "token": token = chunk["content"] full_response += token yield f"data: {json.dumps(chunk)}\n\n" # Step 4.5: 解析 memory_decision ← 新增 memory_decision = extract_memory_decision(full_response) if memory_decision is None: memory_decision = get_fallback_decision() # Step 4.6: 清理回答（移除标签）← 新增 clean_response = remove_memory_decision_tag(full_response) # Step 5: 保存消息（使用清理后的回答） session_manager.save_message(session_id, "user", message) session_manager.save_message(session_id, "assistant", clean_response) # Step 6: 写入 trace（传入 memory_decision） trace = trace_writer.write_trace( session_id=session_id, context_result=context_result, tool_calls=[], memory_decision=memory_decision, # ← 使用解析结果 output_refs=[] ) # Step 7: 发送 done 事件 yield f"data: {json.dumps({'type': 'done', 'trace_id': trace['trace_id']})}\n\n"

Stage 5: 降级策略
可靠性增强

🎯 目标

处理 LLM 不遵守格式的情况，确保系统在任何情况下都能正常运行。

🔧 降级触发条件

  • LLM 未输出 <memory_decision> 标签
  • JSON 格式错误（缺失字段、语法错误）
  • action 字段值不合法（非 "write" 或 "skip"）

💻 降级策略实现

已在 Stage 2 的 get_fallback_decision() 中实现：

# 降级决策：默认 skip { "action": "skip", "target_layer": null, "target_type": null, "target_path": null, "reason": "LLM 未输出 memory_decision，降级为 skip" }

📊 降级策略选择

方案 A：降级为 skip（推荐）
  • ✓ 安全：不会误写 memory
  • ✓ 简单：无需额外逻辑
  • ✗ 可能丢失有价值的 memory 更新
方案 B：降级为规则引擎
  • ✓ 不丢失 memory 更新机会
  • ✗ 复杂：需要维护规则引擎
  • ✗ 准确性低：盲猜决策

📈 监控与优化

建议在 trace 中记录降级事件，用于后续 prompt 优化：

# 在 trace 中新增字段 { "memory_decision": {...}, "memory_decision_source": "llm" | "fallback", # ← 新增 "llm_raw_output": "..." # ← 可选，用于调试 }
⚠️ 降级率监控

建议监控降级率（fallback 次数 / 总对话次数）：

  • < 5%：正常，prompt 工作良好
  • 5-15%：需要优化 prompt
  • > 15%：考虑切换到方案 1（规则引擎）或混合方案

风险与缓解措施

🔴 高风险：LLM 不遵守格式

描述：LLM 可能忘记输出标签或输出格式错误的 JSON

影响：memory_decision 缺失，降级为 skip

缓解：

  • Prompt 中使用强调词（"必须"、"MUST"）
  • 提供多个示例
  • 实现健壮的解析器 + 降级策略
  • 监控降级率，及时优化 prompt
🟡 中风险：JSON 解析失败

描述：reason 字段包含中文引号、换行符等导致 JSON 解析失败

影响：解析失败，触发降级

缓解：

  • 使用 re.DOTALL 处理多行 JSON
  • 在 prompt 中要求 reason 使用简短文本
  • 考虑使用更宽松的 JSON 解析器（如 json5）
🟡 中风险：性能影响

描述：需要收集完整 LLM 输出后才能解析，可能增加延迟

影响：用户感知到的响应时间增加

缓解：

  • SSE 流式输出仍然实时发送给用户
  • 解析和清理在后台异步进行
  • 正则匹配性能足够（<1ms）
🟢 低风险：用户看到内部标签

描述：清理函数失效，用户看到 <memory_decision> 标签

影响：用户体验下降

缓解：

  • remove_memory_decision_tag() 使用健壮的正则
  • 单元测试覆盖边界情况
  • 即使清理失败，标签内容也是 JSON，不影响理解
🟢 低风险：决策不准确

描述：LLM 做出错误的 memory 决策（该写的 skip，该 skip 的 write）

影响：memory 更新不准确

缓解：

  • Prompt 中提供清晰的决策规则
  • Phase 4 引入工具后，LLM 可以先读取 memory 再决策
  • trace 记录完整决策过程，可人工审查
🟢 低风险：模型切换兼容性

描述：切换到不同的 LLM 模型后，遵守格式的能力不同

影响：降级率上升

缓解：

  • 降级策略保证系统可用性
  • 针对不同模型调优 prompt
  • 监控降级率，及时发现问题

总结

✅ 方案 3 的核心优势
  • 准确性最高：LLM 基于实际生成的回答内容做决策，而非盲猜
  • 符合原设计：完全对齐 phase3-index.md 的"生成回答与 memory 决策"设计意图
