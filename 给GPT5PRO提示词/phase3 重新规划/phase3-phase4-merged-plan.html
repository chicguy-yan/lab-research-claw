Phase 3 + Phase 4 合并方案

Tool-Driven Memory Access — 让 LLM 通过工具主动读写 Memory，而非预先注入
System Prompt 极简化 + 按需读取 + 工具调用即决策

🎯 核心理念：从"预测注入"到"按需读取"

原 Phase 3 设计中，ContextOrchestrator 需要预测本轮对话需要哪些 memory 文件，然后注入到 system prompt。 这导致两个问题：① 预测不准确（可能注入无用文件或遗漏需要的文件），② Context 过大（预先注入大量内容）。

新方案采用 Tool-Driven 架构：System Prompt 只包含控制层六大 md（AGENTS.md, SOUL.md, IDENTITY.md, USER.md, SKILLS_SNAPSHOT.md, project.md）， Memory 三层只提供目录结构（文件路径列表）。LLM 看到路径列表后，自己决定需要读取哪些文件，通过 read_file 工具按需读取。 需要写入时，直接通过 write_file 工具写入。工具调用本身就是 memory 访问的决策和审计，不需要额外的 memory_decision 字段。

架构对比

维度 原 Phase 3 设计 新方案（Phase 3+4 合并） 优势
System Prompt 控制层 + 选中的 memory 文件内容 仅控制层 + memory 目录列表 ✓ Context 更小
Memory 读取 ContextOrchestrator 预先选择并注入 LLM 通过 read_file 工具按需读取 ✓ 更灵活，不依赖预测
Memory 写入 memory_decision 结构化输出 直接通过 write_file 工具 ✓ 工具调用即决策
Context 大小 大（预先注入可能用不到的文件） 小（只注入控制层） ✓ 节省 token
灵活性 低（依赖 ContextOrchestrator 预测） 高（LLM 自主决策） ✓ 更符合 Agent 理念
架构复杂度 高（需要 ContextOrchestrator + memory_decision 解析） 低（移除 ContextOrchestrator） ✓ 简化架构
审计 需要 memory_decision 字段 工具调用即审计 ✓ 自然集成
