# Research Closure & Benchmark Spec
## ResearchLoop-OpenClaw 首轮理解材料

## 1. 项目定位

ResearchLoop-OpenClaw 不是普通科研问答助手，而是一个面向长期研究任务推进的 AI-native 工作系统。  
它要解决的问题不是“回答一个科研问题”，而是把真实科研中长期割裂的三条链路连接起来：

- 文献调研
- 实验推进
- 阶段汇报 / 论文写作

系统目标是：  
用 AI 串联并沉淀科研任务流，把实验、文献与阶段成果双向关联，将零散研究过程转化为可持续推进的科研闭环。

## 2. 三个科研闭环场景

### A. literature_closure
目标链路：主题文献 → 研究问题 → 假设 / 证据链  
用于测试系统能否从分散文献、笔记和机理讨论中形成研究主题与证据链，而不是停留在单篇摘要层。  
主要对应 `Concept`，必要时可组织为文献型 `Pack`。

### B. experiment_closure
目标链路：实验目标 → SOP / Protocol → 原始数据 → 结果解释 → 下一步  
用于测试系统能否把实验原理、操作流程、原始数据和结果判断组织成可推进、可复用的 `Task`，而不是停留在零散文件或单轮答复层。  
主要对应 `Task`，必要时可汇总为阶段性 `Pack`。

### C. writing_closure
目标链路：阶段目标 → 结果汇总 → 汇报 / 论文结构  
用于测试系统能否把已有文献主题和实验结果组织成阶段性输出，避免“结果做了但没写出来”。  
主要对应 `Pack`，必要时可回连到底层 `Task` 或 `Concept`。

## 3. 记忆架构与对象设计

本项目参考 OpenClaw 的 File-first 思路，用本地文件管理长期研究过程。

### Layer1 / Layer2
用于承载长期稳定信息与时间推进信息，例如：
- 研究背景
- 项目主线
- 阶段上下文
- 时间线
- 稳定约束

### Layer3
这是本项目的核心抽象，也是科研场景的 sweet point：

- `Concept`：研究主题容器，组织主题文献、研究问题、机理假设
- `Task`：实验任务容器，组织 Claim / Evidence / Protocol / Runs / Missing
- `Pack`：阶段交付容器，组织汇报材料、写作素材、图表集合、论文段落

这套对象设计的目的，是把“文献-实验-写作”三条原本割裂的工作流，转化为统一的科研工作资产系统。

## 4. Benchmark 的真实来源

本项目的 benchmark 不是后期为了评测单独构造的静态问答集，  
而是从最初模拟真实用户提问的过程中自然生长出来的原始数据底座。

项目早期围绕同一研究主线连续记录：
- 多轮提问
- 材料上传
- 任务推进
- 阶段性整理

这些过程数据逐步暴露出三类高频科研闭环场景：
- 文献闭环
- 实验闭环
- 写作闭环

同时也反向推动了本项目的记忆架构与 Layer3 对象设计。

因此，这个 benchmark 不只是“测试集”，更是：
三类闭环场景抽象与 Concept / Task / Pack 设计的来源之一。

## 5. Benchmark 当前定义

该 benchmark 以约 180 天科研生命周期为时间跨度，  
模拟围绕同一研究主线持续推进的研究过程，覆盖文献、实验、写作三类高频任务。

它的重点不是测试“单轮回答是否正确”，而是测试系统是否真的具备：

- 正确组织研究上下文
- 推动科研闭环进入下一步
- 输出可信可用结果
- 沉淀为可复用的研究资产

## 6. 核心评测指标

本项目评测收敛为两个总指标，并采用五级评分制：

### 1. 科研闭环推进成功率
衡量系统是否在一次交互后，基于当前研究阶段、已有材料与任务状态，将用户问题推进到下一步可执行状态。

### 2. 可信可用输出率
衡量系统输出是否基于正确上下文、显式处理不确定性，并可直接用于后续实验设计、数据解释、阶段汇报或论文写作。

## 7. 这份 spec 的用途

这份材料的用途不是介绍全部实现细节，而是帮助模型先准确理解：

1. 这个项目是科研闭环工作系统，不是普通问答助手  
2. 三个闭环场景是产品测试和对象建模的核心框架  
3. benchmark 不是后验题库，而是从真实科研提问与任务推进过程中长出来的数据底座  
4. Layer3 的 Concept / Task / Pack 是本项目最关键的产品抽象
